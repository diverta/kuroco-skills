## プロキシパターンの実装制約

**プラグイン名は`{api}`。`api_request`という名前のプラグインは存在しない**（`{api_internal}`はKuroco自身のAPIを呼ぶ別物）。パラメータの一覧・構文・レスポンス格納（`var`/`json_var`/`status_var`）・キャッシュ（`cache_time`）は SKILL.md「外部API呼び出し › 主なパラメータ」が正。設計段階で効いてくるのは次の3点:

- `files` — **1回の呼び出しで送れるのは1ファイルのみ**。複数ファイルは呼び出しを分ける
- `timeout` — **既定 30 秒、指定できるのは 1〜3600 秒**（`function.api.php`）。遅い外部 API に依存するプロキシは、フロントの待ち時間がそのまま伸びるので、明示的に伸ばすより取り込み（バッチ）に倒すことを検討する
- `sslcert`/`sslkey`/`cainfo` — mTLS 用。値は証明書そのものではなく**シークレットのキー名**

**カスタムエンドポイント1リクエストの PHP 実行時間は30秒**（API エントリの `set_time_limit(30)`）。プロキシでは `{api}` の `timeout` をこれより短く（例: 10秒）し、外部が遅いときはエンドポイント側で打ち切られる前に `status_var` で失敗を返す。数十秒かかる外部 API を待つ必要があるなら、プロキシではなく取り込み（バッチ。実行時間上限は既定4時間・Smarty バッチ6時間）に倒す。

## 取り込みパターン: バッチ vs スパイダー vs Webhook

**スパイダーは構造化APIの定期ポーリングには向かない。** スパイダーは「指定したWebページやファイル（S3バケット等）を巡回し、テキスト・画像・ファイルを収集してKurocoのコンテンツに取り込む」機能であり、対象は非構造データ（Webページ・ファイル）。**巡回自体が課金対象のAPIリクエストを発生させる**ため、コスト面でも構造化APIのポーリング用途には不向き。

外部APIのように構造化されたデータを定期取得する場合は、**バッチ処理**で `{api}` により取得し、`{api_internal}` でTopicsへ挿入/更新する構成にする。再実行で重複しないよう、**外部側の ID を拡張項目に持ち、それで存在チェックしてから insert / update する**（まとめて入れるなら `bulk_upsert`、拡張項目を `filter` に書く構文は `/kuroco-api-content`）。実装の型は「既存を一覧で取って外部ID→topics_id の辞書を作り、差分だけ書く」:

```smarty
{assign var="map" value=$dataSet.emptyArray}
{api_internal endpoint='/rcms-api/3/product' method='GET' member_id=1 queries=$q var='res'}
{foreach from=$res.list item="row"}{append var="map" index=$row.external_id value=$row.topics_id}{/foreach}
{* 以降: isset($map[$ext_id]) なら /update/`$map[$ext_id]`、無ければ /insert *}
```起動回数の制限（無料枠は100回/時）と実行時間上限（4時間、Smarty バッチは6時間）は SKILL.md「バッチ処理」を参照。

外部システム側からのプッシュを受けたいだけなら、**Webhook**やあらかじめ用意された**トリガーメールアドレス**（例: 電話番号宛のメールを送るだけでSMS送信が実行される`{番号}@twilio.r-cms.jp`）で、Smartyコードを書かずに済ませられる場合がある——実装前に SKILL.md「外部サービス連携 › トリガーメールアドレス」の一覧を確認する。

## 秘密情報の管理

APIキー・Webhookの秘密URLなど**攻撃に使われうる値は`{secret}`プラグイン**（[環境設定]→[シークレット]で事前登録）で読み出す。構文と例は SKILL.md「外部API呼び出し」末尾。`$smarty.const.*`（サイト定数）は非秘匿の設定値向けで、秘匿情報の置き場所にしない。mTLS の証明書・鍵・CA 情報も同様に`{secret}`のキー名で参照する。

## トークン管理

外部連携が壊れる原因の多くは「繋がらない」ではなく「繋がっていたが、後からトークンが失効した」。連携先の認証方式ごとに、トークンの性質と管理方針を分けて設計する。

| 認証方式 | トークンの性質 | 管理方針 |
|---|---|---|
| 固定APIキー | 失効しない（回転させない限り） | `{secret}`に登録するだけでよい。最も単純 |
| OAuth2クライアントクレデンシャル | 短命なアクセストークンを都度発行できる（ユーザー文脈なし） | `client_id`/`client_secret`を`{secret}`に置き、**呼び出しの都度その場でトークンを取得**（JIT）してよい。永続化の必要が薄い |
| OAuth2認可コード＋リフレッシュトークン | 長命なリフレッシュトークン＋短命なアクセストークン | リフレッシュトークンは`{secret}`。アクセストークンは**都度リフレッシュして使う**か、更新頻度が低くて済むなら後述の方法で持ち回す |
| 署名付きリクエスト（HMAC等） | トークンではなく毎回の署名 | シークレットキーを`{secret}`に置き、呼び出し直前に署名を計算する |
| **自己更新型の長期トークン**（refresh を呼ぶと**新しいトークンが返り、旧トークンは失効**する。Instagram の60日トークンなど） | 更新のたびに値が変わり、元の値には戻れない | **JIT 取得は不可**（種になる値自体が失効する）。回転後の値を必ず永続化する——下記 2. の保護 Topics レコード。初回だけ `{secret}` に置いた種の値から読む |

**アクセストークンを持ち回す必要がある場合の制約**: `{secret}`は管理画面から登録する仕組みで、**Smartyから値を書き込むプラグインは一次資料から見つかっていない**（読み出し専用の`{secret}`プラグインのみ確認）。そのため、バッチで定期的に更新されるアクセストークンの持ち回し先は、次のいずれかで設計する。

1. **都度取得（JIT）**: プロキシ呼び出しのたびに、まずトークン発行/リフレッシュのAPIを`{api}`で叩いてから本処理を呼ぶ。実装がシンプルだが、呼び出しごとに1往復増える
2. **保護されたTopicsレコードに保存**: 更新バッチが`{api}`でトークンを更新し、`{api_internal}`で非公開の専用コンテンツ（例:「外部連携トークン」定義、`provider` / `access_token` / `expires_at`）へ書き戻す。読む側（プロキシでも取り込みバッチでも同じ）は`{api_internal}`でそのレコードを読んでから外部APIを呼び、レコードが空の初回だけ`{secret}`の種の値にフォールバックする。該当コンテンツは `secure_level` で閲覧制限し、公開エンドポイントに載せない（定義の作り方は `/kuroco-content-structure`）。読む側はエンドポイントを作らず `{api_method model='Topics' method='list' ...}`（GET のみ）で取れる。`expires_at` は `{$smarty.now+$res.expires_in|date_format:"%Y-%m-%d %H:%M:%S"}` のように保存する

**`api_token`プラグインと混同しない。** `api_token`はKuroco自身の静的/動的アクセストークンをSmartyから発行する仕組みであり（`{api_internal}`呼び出し用のトークンをその場で用意する等に使う）、**外部システムのOAuthトークンの管理とは無関係**。

長期間有効なトークンでも更新が必要になる例（Instagram の長期アクセストークンは60日で失効）があるため、**「失効しないトークン」だと思い込まず、連携先のドキュメントで有効期限とリフレッシュ手段を必ず確認し、更新用バッチの要否を設計に含める。**

## 直接呼び出しパターンの注意

KurocoFrontの設定（`kuroco_front.json`）はrewrites・Basic認証・IPアドレス制限のみを扱い、**フロントエンドからの外向き呼び出しを制限するCSP等の仕組みは無い。** 直接呼び出しパターンのCORS可否は完全に**相手の外部API側のポリシー次第**であり、Kuroco側で制御できる余地はない。相手がCORSを許可していない場合、直接呼び出しは選べない（プロキシに切り替える）。

## 実例から見える落とし穴

| 連携先/サービス | パターン | 落とし穴 |
|---|---|---|
| Instagram（自社投稿の取り込み） | 取り込み（バッチ） | 長期アクセストークンは**60日で失効**し、refresh すると新トークンに置き換わる（旧 Basic Display API も後継 API も同じ仕組み）。トークン更新を行う別バッチと、回転後の値の保存先（保護 Topics レコード）を用意しないと数ヶ月で止まる。設計時点でこの運用コストを見積もる |
| Twilio（SMS送信） | 3パターンの外（通知送信） | `{tel}@twilio.r-cms.jp` 宛にメールを送るだけでSMSが送れる（トリガーメールアドレス、Smartyコード不要）。個別実装より先にこの方式で足りないか確認する |
| Slack / LINE | 送信と受信で分けて考える | **通知送信**は3パターンの外——トリガー処理から `slack_post_message`（サイト設定のSlack連携。Webhook URLは使わない）／`{LINE ID}@text.line.r-cms.jp` 宛のトリガーメール。**受信**（メッセージをKurocoに保存）はWebhookをKuroco側で受ける取り込み。**Messaging APIを自分で叩く**ならプロキシかバッチで`{api}`。いずれも外部サービス側のOAuthアプリ登録・Bot設定が主なセットアップコスト |
| Amazon S3 / Vimeo / Google Analytics | 秘密情報が前提の連携 | いずれも`{secret}`に登録した認証情報の取り扱いが起点になる。連携先ごとに必要な認証情報の種類を先に確認する |

## 設計成果物テンプレート

```markdown
## 外部連携: {連携先名}
- パターン: 直接呼び出し / プロキシ / 取り込み（バッチ｜スパイダー｜Webhook）
- 秘密情報: {secret}に登録する項目一覧
- トークンの性質: 固定キー / クライアントクレデンシャル / リフレッシュトークン付き / 署名方式
- トークンの持ち回し方針: JIT取得 / 保護Topicsレコードに保存（該当する場合）
- 運用コスト: トークン更新など定期メンテが必要か、有効期限は何日か
- タイムアウト: 相手APIの応答時間の想定と `{api}` の `timeout` 設定値（プロキシならエンドポイントの30秒制限より短く。バッチなら既定30秒・最大3600秒）
```

## アンチパターン

| してはいけないこと | 理由 |
|------|------|
| スパイダーで構造化APIを定期取得しようとする | スパイダーはWebページ・ファイルの巡回用。構造化データはバッチ処理＋`{api}`が適切 |
| APIキー・Webhookの秘密URLを`$smarty.const.*`（サイト定数）に置く | 非秘匿の設定値向けの仕組み。攻撃に使われうる値は`{secret}`に置く |
| `api_request`という名前のプラグインを探す・使おうとする | 存在しない。正しいプラグイン名は`{api}` |
| 外部APIの応答時間を確認せずプロキシパターンを採用する | `{api}` は既定30秒で打ち切られ、フロントはその間待たされる。遅い外部APIなら取り込み（バッチ）に倒す |
| 長期アクセストークンを使う連携で、トークン更新の運用コストを見積もらない | 例: Instagram Basic Display APIは60日で失効し、更新用の別バッチが必要になる |
| ローテーションが必要なアクセストークンを`{secret}`に書き込もうとする | Smartyから`{secret}`の値を更新するプラグインは確認できていない。JIT取得か、保護されたTopicsレコードへの保存で設計する |
| `api_token`プラグインで外部システムのOAuthトークンを管理しようとする | `api_token`はKuroco自身のトークン発行用。外部システムのトークンとは無関係 |
