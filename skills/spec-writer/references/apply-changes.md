# 仕様書からの反映プロトコル（往復運用）

ユーザーが生成済み仕様書を編集し、「この仕様書どおりに変更して」と依頼したときの手順。
**このフローは書き込みを伴うため、spec-writer 本体（読み取り専用）の範囲外。**
書き込みの承認・実行ルールは `/kuroco-admin-mcp`、コンテンツ定義の変更構文は
`/kuroco-content-structure` に従い、本ファイルは**仕様書の解釈と差分計画の作り方**だけを定める。

## 大原則

1. **仕様書のスナップショットを現況とみなさない。** 仕様書は生成日時点の写しであり、その後サイト側が変わっている可能性がある。反映前に必ず現況を再取得し、「編集後の仕様書」と「現在のサイト設定」を比較する
2. **差分計画を提示して承認を得るまで書き込まない。** 破壊的変更を含む場合は `site-backup` を先に取る
3. **IDはメタデータコメントと現況取得で解決する。** 推測しない。メタデータコメントが無い・古い場合は識別子（ext_slug 等）で `*-list` から引き直す
4. **書き込みの成功レスポンスを反映の完了とみなさない。** 書き込み後に必ず読み戻して、送った値が保存されているかを照合する（宣言済みのパラメータが黙って無視される書き込みツールがあり、成功応答でも保存されていないことがある）。詳細は `/kuroco-content-structure`
5. **反映が終わったら、変更した章の仕様書を再生成して現況と同期する。** 同期しないと次回の反映で偽の差分が出る

## IDと識別子の解決

| 仕様書上の表記 | 反映時に解決するもの | 解決方法 |
|--------------|-------------------|---------|
| ページキー（ファイル名・ER図のノード名。`tg{topics_group_id}_{名前}`） | 先頭の `topics_group_id` だけが実体を指す。**名前部分は何も指さない**（仕様書内の便宜キー） | メタデータコメントの `id` と、ページキー先頭の `topics_group_id` が一致するか照合する（食い違えばファイルの取り違えなので、反映せず報告する）。**ページキーの変更は反映対象ではない**——リネーム依頼と解釈せず、必要なら意図を確認する |
| 項目表の識別子列 | 拡張項目 | `topics_group-get` で現況の `ext_slug_N` と突き合わせ、スロット（`ext_N` / `topics_group_ext_id_N`）へ解決する。`ext_1` 等のスロット名が書かれている行はそれ自体が識別子 |
| 選択肢の `` `キー`: ラベル `` | 選択肢 | キーが同じでラベルだけ違う=表示名の変更、キーが増減=選択肢の追加・削除。**キーが書かれていない編集はキーを推測せず質問する** |
| 会員グループ名 | `group_id` | `group-list` から名称で引く。同名が複数あれば質問する |
| エンドポイントのパス | `api_uri_id` | `api_uri-list` から `api_id` + `api_uri` で引く |

## 手順

### Step A: 対象の特定

**最初に「生成時の仕様書」が手に入るかを確認する。** 3者比較の第3軸がこれで、
無いと「ユーザーが追加した行」と「サイト側で消えた項目」が同じ形（仕様書にあり・現況になし）になり、
**新規作成と反映禁止という真逆の扱いを見分けられない**。

| 生成時スナップショットの入手 | 進め方 |
|--------------------------|-------|
| Git 管理下（`git diff` / `git show HEAD:<path>` が使える） | そのまま3者比較へ |
| 管理外だが生成時のコピー・PDF・zip が残っている | それを第3軸として使う |
| 生成時の `schema/` の定義ファイル（OpenAPI・`topics_group-get` の生レスポンス）が残っている | Markdown の第3軸に加えて使う。**生成時の実設定そのもの**なので、現況の同じツールの戻り値と機械的に比較できる（Markdown の表より精度が高い）。ただし**これも生成日時点のスナップショットで、現況ではない** |
| どこにも無い | **「編集箇所を特定できない」と宣言し、ユーザーにどこを編集したかの申告を求める。** 申告された箇所だけを反映対象とし、それ以外の食い違いはすべて「乖離（要確認）」として報告する。推測で編集箇所を決めない |

- ユーザーの指示か、Git 管理下なら `git diff` で編集されたページを特定する
- 各ページ先頭の `kuroco-spec` メタデータコメントから対象リソース（`topics_group_id` 等）・`generated_at`・`tools`（生成時に呼んだ読み取りツール）を読む

### Step B: 現況の再取得と3者比較

**メタデータコメントの `tools` に並んでいるツールを呼び直して現況を取る**（生成時と同じ経路なので比較が1対1になる）。
`tools` が無い・現在の接続でそのツールが見えない場合は、ツール一覧から同じリソースの読み取りツールを引き直し、
**経路が変わったことを差分計画に明記する**（取得できる範囲が違えば差分の意味も変わる）。取得したら3者を比較する:

| 比較 | 意味 |
|------|------|
| 編集後の仕様書 vs 現況 | **反映すべき差分の候補**（ここから変更計画を作る） |
| 生成時の仕様書 vs 編集後の仕様書 | **ユーザーが編集した箇所**（Git 管理下なら `git diff`。編集していない箇所と切り分けるための軸） |
| 生成時の仕様書 vs 現況 | **仕様書と現況の乖離**。ユーザーの編集とは無関係に生じている |

**報告するかどうかは「ユーザーが触ったか」で決めない。「その書き込みが誰かの変更を打ち消すか」で決める。**
ユーザーが編集していない箇所の乖離は、気付かれないぶん危険度が高い:

| 状況 | 扱い |
|------|------|
| 仕様書（生成時から未編集）と現況が食い違う | **反映せず報告が既定。** 仕様書の記述で上書きすると、生成後の他者の変更を巻き戻す。ユーザーの編集ではないので変更計画に入れない |
| ユーザーの編集箇所が現況とも食い違う（編集が古い前提に基づく） | **反映せず報告。** どちらを正とするかはユーザーの判断 |
| ユーザーの編集箇所で、現況が生成時と同じ | 通常の反映対象。変更計画に入れる |

**「A と B が違う」ことと「A が B に変わった」ことは別の主張。**
「生成後にサイト側で変更された（ドリフト）」と書くには、変更の向きを履歴で裏取りする:

根拠には強さの差がある。**一次証拠だけが断定に使える:**

| 種別 | 例 | 使い方 |
|------|-----|-------|
| 一次証拠 | 更新日時（`update_ymdhi` / `inst_ymdhi`）、履歴レコード、操作ログ | 断定の根拠にできる |
| 構造的傍証 | IDの連続性（`topics_group_ext_id` に欠番が無い）、件数の整合 | **結論を格上げしない。** 断定には使わないが、示唆として併記する（読者が判断材料にできる） |

**根拠の入手可能性に応じて、書き方を3段で使い分ける。裏取りできないことを「報告しない理由」にしない**（乖離自体が報告から落ちるのが最悪）:

| 根拠 | 書き方 |
|------|-------|
| 更新日時・履歴で生成後の変更を確認できた | 「生成後にサイト側で変更された（ドリフト）」と断定し、根拠（更新日時・履歴レコード）を添える |
| 履歴は引けたが変更が特定できない／更新日時が生成日より前 | 「仕様書と現況が食い違う。生成後のサイト側変更か、生成時の記述誤りかは**判定不能**」と書き、**判定不能の理由**（何を見て、なぜ決められなかったか）を必ず併記する |
| 裏取り手段が構造的に無い（履歴ツールが一覧に無い、ログの保持期間が足りない等） | 上と同じ形で書き、**どのツールがどの制約で使えなかったか**まで書く。読者が「調べていない」と「調べられない」を区別できるようにする |

いずれの場合も、どちらを正とするかの判断はユーザーに返す（勝手に反映しない）。

**リソースごとの裏取り可用性は既知なので、毎回調べ直さない:**

| 対象 | 可用性 |
|------|-------|
| APIエンドポイント | **1段目（断定できる）。** `api_uri_history-list` → `api_uri_history-get` で更新履歴が引ける |
| コンテンツ定義の項目の増減 | 定義の変更履歴を引く読み取りツール（名前は接続中の一覧が正）で裏取りする。一覧に見えなければ3段目として扱う。`topics_history-get` は**レコード**の履歴で定義の履歴ではないので、これで代用しない |
| どのリソースでも | `admin_log-list` は**直近12時間の範囲しか照会できない**（かつ5秒に1回の頻度制限）。生成から1日以上経っていれば使えない |

**`update_ymdhi` を「項目は変わっていない」の根拠にしない。** 定義ヘッダーの更新日時であり、
拡張項目は別レコード（`topics_group_ext_id`）なので、項目の増減を反映するとは確認できていない。
ヘッダーの更新日時が生成日より前でも、項目が増減していない証明にはならない。

### Step C: 差分計画の提示と承認

**提示の章立てはここで決める。**（分類ルールは「どの章に載るか」を指すだけで、置き場所を独自に決めない）

1. **対象の特定** — 解決したIDとその根拠
2. **反映する変更** — 下の4列表。非破壊 → データ影響あり → 破壊的の順
3. **削除の提案** — 破壊的変更を別掲。1件ずつ個別確認
4. **反映しない差分** — 乖離（要判断）・参考値・同期タスクをここに集約する。1つの差分が複数分類に該当するときは、この章に1度書き、反映しない理由と同期での扱いを併記する
5. **実行順とバックアップ**
6. **承認のお願い** — 部分承認の選択肢を具体化する

変更を表で提示し、承認を得る:

| 対象 | 操作 | 変更内容 | リスク |
|------|------|---------|--------|
| product.maker_id | 更新 | 必須: なし → あり | 既存レコードに空値があると保存時エラーになる |
| product.old_note | **削除** | 項目を削除 | **投入済みデータが失われる** |

- 破壊的変更（項目削除・型変更・定義削除・API削除）は太字で明示し、**1件ずつ個別に確認する**
- **既存データに影響する変更のリスクは一般論で書かず、件数で定量化する**（項目削除・型変更・選択肢の削除だけでなく、**必須化**も含む——既存の空レコードが保存できなくなる）。
  「データが失われる」より「16件すべてに値が入っており、その入力内容が失われる」のほうが承認の判断材料になる。
  そのための条件付き件数取得は、実データを取らないルールの**明示的な例外**:
  - `topics-list` を `filter`（対象項目が空でない等）+ `cnt=1` + `columns=` 主キーのみで呼び、`pageInfo.totalCnt` だけを読む。レコードの中身は取らない
  - **フィルタが効いていることを逆条件でも1回引いて確かめる。** 合格条件は「条件の件数 + 逆条件の件数 = 総件数」。一致しなければフィルタが意図どおり効いていないので、件数を根拠に使わない
  - **合計一致は「分割が網羅されている」証明にすぎず、条件式が意図と合っている証明ではない。**
    「空」を数えるなら `= NULL` と `= ""` の**両方**を引く（NULL と空文字は別物で、`= NULL` だけでは空文字が非空側に混ざる）
- **部分承認を提示してよい。** 非破壊の変更だけ先に実行し、破壊的変更は保留する、という選択肢を承認のお願いに含める（全部か何もしないかの二択にしない）
- 承認後、破壊的変更があれば `site-backup`（memo付き）→ `site_backup-list` で ready を確認してから実行
- **実行順を計画表に書く。** 既定は「バックアップ → 非破壊の更新 → 追加 → 破壊的変更」。
  破壊的変更を最後に置けば、途中で停止したときの被害が小さい。削除は**明示の承認が出るまで実行しない**（承認が無ければスキップし、仕様書側に行を戻す）
- **反映対象外と判定した差分を計画から落とさない。** 「反映対象外」は「対応不要」ではない。
  参考値のずれ（件数・生成日・ID・ページキー）や、ユーザーが編集していない本文の陳腐化は、
  変更計画とは別に「同期で直す項目」として列挙し、Step E で処理する。落とすと次回も同じ差分が出る

### Step D: 反映の実行と読み戻し

- コンテンツ定義 → `/kuroco-content-structure`、API → `/kuroco-admin-mcp`（`api-upsert_*`）、その他も各スキル・ツールの規約に従う
- 書き込みは1件ずつ順に実行する（並列にしない）
- **現況の項目セットを土台に、承認された差分だけを当てる。仕様書の項目表を丸ごと流し込まない。**
  丸ごと流すと、Step B で「反映しない」と判断した乖離（仕様書にあってサイトに無い項目など）まで一緒に書き戻り、
  報告して保留したはずの変更が実行される。**承認された行以外は現況のまま送る**
- 実行順は「非破壊の更新 → 追加 → **既存データに影響する更新（必須化・型変更・選択肢の削除）** → 破壊的変更（削除）」。
  必須化は非破壊ではないので追加より後に置く
- **1件書いたら読み戻して照合する。** コンテンツ定義なら `topics_group-get` で対象項目の
  `ext_slug` / `type` / `limits`（必須）/ `options`（選択肢）/ `ext_group_loop` が意図どおりかを確認する。
  成功応答だけを根拠に次へ進まない
- 照合で食い違いがあれば**そこで止めて報告する**。残りの変更を続けて差分を積み増さない
- 既存項目の変更は、送らなかった属性が初期化されないかを1件目で確認してから残りを流す

### Step E: 仕様書の同期

- 変更した章のページを実設定から再生成する（該当ページのみでよい）
- **Step C で「反映対象外」に振った差分をここで消化する**（参考値の更新、陳腐化した本文の書き直し、承認が出ずスキップした削除行の復帰）。ここで処理しないと次回の反映で同じ差分が再び出る
- メタデータコメントの `generated_at` を更新する
- Git 管理下ならユーザーにコミットを促す（仕様書の履歴＝設定変更の履歴になる）

## 編集の解釈ルール

仕様書の編集をどんな操作として解釈するか。**曖昧な編集は推測せず質問する。**

**1つの差分が複数の分類に該当することがある。分類は排他ではない。**
たとえば件数のずれ（生成時4 / 編集後12 / 現況16）は「参考値＝反映しない」と
「サイト側が変わった証拠＝報告する」の両方に該当する。この場合は**両方に載せる**——
反映計画には入れず、乖離の報告にも1行書く。片方だけ書くと、反映しない判断か見落としかが読者に伝わらない。

| 仕様書の編集 | 解釈 |
|-------------|------|
| 項目表への行追加 | 項目の新規作成。`ext_slug` が空欄なら命名を提案して確認する |
| 項目表の行削除 | 項目の削除**提案**。データ喪失を伴うため、Step C で必ず個別確認する。黙って実行しない |
| セルの値変更 | その属性の更新（名称・必須・選択肢など） |
| 識別子セル（ext_slug 等）の変更 | **リネームと解釈しない**（削除+新規=データ喪失の可能性）。`（旧: old_slug）` 併記があればリネーム意図として扱い、実現方法を確認する。併記が無ければ質問する |
| 選択肢のラベルだけの変更 | 表示名の更新。キーは変えない |
| 選択肢のキーの追加・削除 | 選択肢の追加・削除。削除は既存レコードにその値が入っている可能性があるため、行削除と同じく個別確認する |
| 型セルの変更 | 型変更。破壊的変更として扱う（既存データの解釈が変わる） |
| 参考値（件数・生成日・topics_group_id・ページキー/ファイル名）の変更 | 反映しない。参考値である旨を伝え、**Step E では編集後の値ではなく現況の実測値へ更新する**（生成時4・編集後12・現況16 なら 16 に直す） |
| 本文（用途説明・処理概要）だけの変更 | 設定変更なし。ただし処理概要とカスタム処理の実装が乖離する編集なら、実装変更の意図か確認する |
| 新しいページの追加 | コンテンツ定義・API 等の新規作成。`/kuroco-content-structure` の Part 1 で設計を確認してから作成する |
| ページの削除 | 定義・API の削除提案。最も破壊的な操作として扱う |

## アンチパターン

| やりがち | 問題 | 推奨 |
|---------|------|------|
| 仕様書と現況の比較を省いて仕様書の記述をそのまま流し込む | ドリフトを上書きし、他者の変更を破壊する | Step B の3者比較を必ず行う |
| 未編集の行と現況の食い違いを「行があるのに無いから新規作成」として実行 | 生成後に他者が削除したものを復活させる。編集差分（`git diff`）だけを見ると必ずこの罠に落ちる | 「生成時 vs 現況」の軸を必ず見る。未編集箇所の乖離は報告 |
| 「生成後に変更された」と履歴を確認せず書く | 実際は生成時の記述誤りかもしれない。誤った原因をユーザーに信じさせる | 更新日時・履歴で裏取りし、取れなければ両可能性を提示 |
| 反映対象外と判定した差分をその場で捨てる | 陳腐化した記述が残り、次回の反映で同じ差分が再発する | 同期タスクに送って Step E で消化する |
| 行削除を編集意図と断定して削除を実行 | 表の整理のつもりの編集でデータが消える | 削除は常に「提案」。個別確認してから |
| 反映後に仕様書を再生成しない | 仕様書と現況が再び乖離し、次回の反映で偽差分が出る | Step E を反映作業の一部として扱う |
| 識別子の変更をリネームとして自動処理 | Kuroco 側の実現方法（新設+移行+削除）は自明でなく、データ喪失リスクがある | 意図と手順を確認してから |
| 書き込みの成功応答を見て完了報告する | 宣言済みのパラメータが無視され、保存されていないことがある | 1件ごとに読み戻して照合してから次へ |
| ファイル名（ページキー）の変更をリネーム依頼として扱う | ページキーの名前部分は仕様書内の便宜キーで、Kuroco 側に対応する設定が無い（先頭の `topics_group_id` だけが実値） | 反映対象外として扱い、必要なら意図を確認する |
