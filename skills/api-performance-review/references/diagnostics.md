# 症状別 調査レシピ

各レシピは **調べ方 → 判定基準 → 典型原因 → 次のアクション** の順。
クエリ例の `<...>` は実値に置き換える（そのままでは実行できない形にしてある）。

---

## 1. キャッシュ比率が低い

**調べ方**

```json
// tool: api_uri-list
{ "api_id": <対象APIのID> }
```

`uri_data` の `cached_api_count ÷ (api_count + cached_api_count)` を直近8日間の比率として出す。
全体傾向は `api_analytics-list` を `cache_status` ごとに集計して求める。

**判定基準**

| 観測 | 判定 |
|------|------|
| `cache_settings.maxage` が無い / 0 | **設定不備**。キャッシュ自体が無効 |
| `maxage` はあるが `cache_status = PASS` が多い | キャッシュ不可の設計（更新系、認証、`Cache-Control` を無効化する処理） |
| `maxage` はあるが `MISS` が多い | キャッシュキーが分散している（→ レシピ2） |
| HIT はしているが件数自体が多い | 設定ではなくリクエスト数の問題（→ レシピ4・5） |

**典型原因と対策**

- TTL 未設定 → 管理画面のエンドポイント設定で秒数を入れる。1日〜1週間が推奨。
  コンテンツ更新時に自動クリアされるため長めでも問題になりにくい
- Cookie 認証 → セッションごとにキャッシュが作られる。認証不要のエンドポイントは
  静的アクセストークンに変更するとトークン単位のキャッシュになり比率が上がる（フロント改修が必要）
- 動的トークン → ユーザーごとにキャッシュが分かれる。共有可能なデータは
  認証不要エンドポイントへ分離できないか検討する
- API 単位の IP 制限 / 管理画面の IP 制限が有効 → **クライアント IP ごとに
  キャッシュが生成される**。制限が必要かを見直す

詳細なレバーは `cache-tuning.md`。

## 2. TTL は十分なのに MISS が多い

**調べ方**

```json
// tool: api_analytics-list
{ "timestamp_start": "<開始 YYYY-MM-DD HH:MM>", "timestamp_end": "<終了 YYYY-MM-DD HH:MM>",
  "filter": "cache_status = \"MISS\"", "sort": "hit", "desc": true, "cnt": 50 }
```

続けて、MISS の多い URI について直近12時間の生ログを見る。

```json
// tool: api_log-list
{ "timestamp_start": "<直近12時間内>", "timestamp_end": "<同上>",
  "filter": "cache_status = \"MISS\"",
  "columns": ["timestamp", "uri", "request_user_agent", "geo_country_code", "status"],
  "cnt": 200 }
```

**判定基準**

- MISS の URI が**詳細ページ（ID やスラッグを含む深い URL）に散っている**
  → キャッシュキーは URL 単位なので、URL の種類が多いほど個々のキャッシュは温まらない
- MISS の UA にクローラーが多い / 国コードが想定と異なる
  → 網羅巡回によるロングテールアクセス（→ レシピ6）
- 特定の1 URL に MISS が集中している → TTL より短い間隔でキャッシュがクリアされている
  可能性。コンテンツ更新頻度と、同一コンテンツ定義グループの更新を確認する

**次のアクション**

- キャッシュクリアの範囲を理解した上で設計を見直す。コンテンツ更新は
  **同じコンテンツ定義グループのエンドポイント全体**をクリアする
  （`Topics::details` のみコンテンツ ID 単位）
- 更新の影響を受けないデータは、自動クリア対象外のエンドポイント
  （`Api::request_api` 等）に分けるとキャッシュが残る。ただしクリアを自前で設計する必要がある
- クローラー起因なら robots.txt / WAF での制御を検討（SEO に必要なクローラーは除外しない）

## 3. 1リクエストあたりは軽いのに件数が跳ねている

**調べ方**

`api_analytics-list` を前年同期（または増加前の同じ日数）と2回に分けて取得し、
エンドポイントごとの倍率を出す。**まず全体の倍率（ベースライン）を出す**。

**判定基準**

- ほぼ全エンドポイントが同じ倍率 → 自然増。異常ではない
- 一部だけがベースラインを大きく超える／新規に出現 → 構造変化。フロント側の変更を疑う
- `body_size` が極端に小さい（数百バイト）のに件数が多い
  → ポーリング、または全ページ設置されたウィジェット系エンドポイント

**次のアクション**

フロント実装で該当エンドポイントの呼び出し箇所を確認する。
ページ内で結果を共有する、呼び出し頻度を下げる、SSG に寄せる、で大半が削減できる。
**ログだけで「ポーリングである」と断定しない**（呼び出し間隔は生ログの
`timestamp` と `client_ip` の分布で確かめる）。

## 4. 1ページビューあたりのリクエストが多い（N+1）

**調べ方**

```json
// tool: api_log-list
{ "timestamp_start": "<直近12時間内>", "timestamp_end": "<同上>",
  "filter": "request_referer contains \"<対象ページのURL>\"",
  "columns": ["timestamp", "uri", "client_ip", "request_referer"],
  "cnt": 300 }
```

同一 `client_ip` × 近接 `timestamp` でまとめ、1ページビューあたりの本数と
URI の組み立てパターンを見る。

**判定基準**

一覧を1本取得したあと、その要素数だけ個別エンドポイント（詳細・関連一覧など）が
連続している → N+1 ファンアウト。要素数・項目数が増えるたびにリクエストが線形に増える。

**次のアクション**

- 一括取得できる形（`Topics::list` に必要項目を含める、フィルタで複数 ID をまとめる）に寄せる
- 1回のレスポンス件数は 20〜200件程度が目安。後処理で項目を絞るならさらに増やせる
- 大量取得はレスポンス生成時間（コンピューティング課金）とのトレードオフになる

## 5. 400/PASS が定常的に出ている

**調べ方**

```json
// tool: api_analytics-list
{ "timestamp_start": "<開始>", "timestamp_end": "<終了>",
  "filter": "status >= 400", "sort": "hit", "desc": true, "cnt": 50 }
```

該当 URI の実際のクエリ文字列は生ログ（`uri` 列）で確認する。

**判定基準**

- クエリに `undefined` / `null` / 空文字がそのまま入っている → フロントの状態管理バグ
- `cache_status = PASS` → **永久にキャッシュされない**。全件が非キャッシュ単価で課金され、
  さらに実行時間ぶんのコンピューティング課金も乗る

**次のアクション**

修正コストがほぼゼロで効果が確実なので、**費用の大小にかかわらず最優先で報告する**。
費用面だけでなく「フロントに不整合がある」というシグナルとして伝える。

## 6. クローラー・海外からのアクセスが多い

**調べ方**

```json
// tool: api_log-list
{ "timestamp_start": "<直近12時間内>", "timestamp_end": "<同上>",
  "columns": ["timestamp", "uri", "request_user_agent", "geo_country_code", "cache_status"],
  "cnt": 500 }
```

UA に `bot` / `spider` / `crawler` を含む比率、`geo_country_code` の分布、
それぞれの `cache_status` 内訳を出す。

**判定基準**

- 日本国内向けサイトで国外比率が高い → 大半がクローラー
- クローラーの `cache_status` が MISS 寄り → 深いアーカイブの網羅巡回

**次のアクション**

- UA は自己申告なので**比率は概算である旨を明記する**
- 検索流入に必要なクローラー（Googlebot 等）は除外できない。
  制限対象は事業上不要なものに限る
- robots.txt / WAF / レート制限（`rate_settings`）のどれで制御するかは
  ユーザーの運用方針を確認してから提案する

## 7. 0バイト応答が大量にある（CORS プリフライトの疑い）

ブラウザからカスタムヘッダ（`X-RCMS-API-ACCESS-TOKEN` など）を付けて
クロスオリジンで呼ぶと、本番リクエストの前に**プリフライト（OPTIONS）**が飛ぶ。
これも CDN／API のリクエストとして計上される。

**調べ方**

```json
// tool: api_log-list
{ "timestamp_start": "<直近12時間内>", "timestamp_end": "<同上>",
  "columns": ["timestamp", "uri", "request", "cache_status", "status", "body_size",
              "execution_time", "api_access_token", "rcms_request_id"],
  "cnt": 500 }
```

**判定基準（すべて揃ってはじめて「プリフライトらしい」と言える）**

- レスポンスサイズ 0 バイト
- `api_access_token` が空（プリフライトはカスタムヘッダを送らない）
- `execution_time` が 0（アプリ層に到達していない）
- `rcms_request_id` が空
- 同一 URL の実リクエストの直前に対で現れる

**確認せずに断定しないこと。** ログ上の HTTP メソッド表記だけでは
プリフライトかどうかは確定できない。以下のいずれかで裏を取る。

1. ブラウザの開発者ツール／HAR で、該当エンドポイントに OPTIONS が発生しているか確認する
2. フロント実装が認証ヘッダを送っているか確認する
3. ログ上の計上ルール（OPTIONS がどのメソッドとして記録・課金されるか）を
   Kuroco サポートに照会する

**次のアクション**

- **`Access-Control-Max-Age` を延ばす**のが副作用の小さい第一手。既定は 600 秒で、
  ブラウザはこの秒数だけプリフライト結果をキャッシュする。
  `api-upsert` の `cors.maxAge` で変更できる（**承認必須**）。
  変更直後は旧値の残存時間だけ反映が遅れる
- 根本的に無くすなら、カスタムヘッダを使わない形（クエリパラメータ、Cookie）にすると
  GET が単純リクエストになりプリフライト自体が発生しない。
  **セキュリティ方式の変更とフロント改修を伴うため、影響評価とユーザー承認が必須**

## 8. 実行時間が長い / コンピューティング費用が気になる

**調べ方**

```json
// tool: api_analytics-list
{ "timestamp_start": "<開始>", "timestamp_end": "<終了>",
  "sort": "execution_time_additional", "desc": true, "cnt": 50 }
```

**判定基準**

- `execution_time_additional` は **300ms を超えた分の合計**で、これがコンピューティング課金の実体
- `cache_status = HIT` の行では実行時間は `" - "`（オリジンに到達していない）。
  遅さの評価は MISS/PASS 行で行う

**次のアクション**

- 費用として意味があるかを先に確認する。コンピューティングは請求全体では
  小さいことが多く、**金額の寄与を見ずに最適化を提案しない**
- 取得件数を絞る、後処理の出力許可リストで項目を減らす、内部呼び出しを
  `{api_method}` / `direct=true` に置き換える
- レスポンス時間そのものが UX 上の課題である場合は、費用と切り離して報告する

## 9. 転送量が増えた

**調べ方**

`usage-get` の `usage_list` で `api_traffic` / `front_traffic` / `img_traffic` を分けて見る。

**判定基準**

3つのうちどれが増えているかで対策先がまったく違う。

| 増えている項目 | 対策の方向 |
|----------------|-----------|
| `img_traffic`（KurocoFiles） | 画像の動的変換で適切なサイズを配信する。元画像の最適化 |
| `front_traffic`（KurocoFront） | 404 などエラーページの軽量化、不要なアセットの削減 |
| `api_traffic` | 後処理の出力許可リストで返す項目を絞る |

**次のアクション**

API 側の項目削減は、転送量の内訳で API が支配的な場合にのみ費用対効果がある。
画像が支配的なら、API 最適化の目的は転送量ではなく**リクエスト件数の削減**だと明記する。

## 10. ファイル容量が増え続けている

**調べ方**

`usage-get` の `usage_list` で `files_bytes` / `front_bytes` / `db_bytes` /
`log_bytes` / `backup_bytes` の推移を見る。

**判定基準**

単調増加で一度も減っていない → 削除運用が存在しない。API 起因ではない。

**次のアクション**

- KurocoFront: 「90日以上前のファイルを削除する」設定の有効化、静的ファイルの KurocoFiles 移動
- DB: 更新履歴を残さない設定（**削除した履歴は復元できない**）
- バックアップ: 不要世代の削除。`{backup}` / `{backup_delete}` によるバッチ運用
- ファイルストレージは**月内最大値で課金される**ため、棚卸しは月内早期に行うほど効く
