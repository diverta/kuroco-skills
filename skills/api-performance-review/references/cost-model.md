# Kuroco の課金モデルとコスト分析

出典: [利用状況](https://kuroco.app/ja/docs/management/usage/) /
[Kuroco利用料の最適化](https://kuroco.app/ja/docs/tutorials/how-to-optimize-kuroco-usage-costs/)。
同梱の kuroco-docs スキルからも参照できる（`../../kuroco-docs/docs/management-misc.md`（`usage`）,
`../../kuroco-docs/docs/tutorials-misc.md`（`how-to-optimize-kuroco-usage-costs`））。

---

## 計算式

```
費目ごとの費用 = ceil(実カウント ÷ UNIT) × 単価
```

公式ドキュメントの例: APIリクエストが 100 hit、UNIT が 1000 hit、単価 55円のとき、
100 ÷ 1000 = 0.1 → 切り上げて 1 → **55円**。

- 端数は常に切り上げ。**小さなリクエストでも1単位分の課金が発生する**
- 月内の合算が請求額になる。**ただしファイルストレージ系だけは集計期間中の最大値**が使われる
  （月中に一度膨らむとその日の値で課金される）

## 利用状況の項目と課金費目の対応

| 利用状況の項目（`usage_list` のカラム） | 課金される費目 |
|------|------|
| キャッシュされたAPIリクエスト（`cached_api_count`） | キャッシュされたAPIリクエスト |
| APIリクエスト（`api_count`） | APIリクエスト |
| API転送量（`api_traffic`） | CDN転送量 |
| API追加処理時間（`api_execution`） | コンピューティング |
| KurocoFront転送量（`front_traffic`） | CDN転送量 |
| KurocoFiles転送量（`img_traffic`） | CDN転送量 |
| メール（`mail_count`） | メール |
| AI処理ユニット（`openai_unit`） | AI処理ユニット |
| バッチ処理時間（`batch_execution_time`） | コンピューティング |
| DBファイル容量（`db_bytes`） | ファイルストレージ |
| ファイル容量（`files_bytes`） | ファイルストレージ |
| KurocoFrontファイル容量（`front_bytes`） | ファイルストレージ |
| ログ容量（`log_bytes`） | ファイルストレージ |
| バックアップファイル容量（`backup_bytes`） | ファイルストレージ |

**「CDN転送量が増えた」だけでは対策が決まらない。** API・フロント・画像の
3つの利用状況項目に分解してから原因を追う（画像が支配的なケースが多く、
その場合 API のレスポンス削減をしても費用はほとんど動かない）。

同様に「コンピューティング」は API 追加処理時間とバッチ処理時間の合算である。

## 単価の逆算手順

契約により単価は異なる。実績から逆算する。

1. `usage-get` で対象月の `cost_site`（費目別金額）と `usage_list` の合計行（費目別カウント）を取る
2. 費目ごとに `金額 ÷ カウント` を計算する（例: APIリクエスト費用 ÷ api_count = 円/リクエスト）
3. **キャッシュ有無の単価比を出す**（キャッシュされたAPIリクエスト単価 : APIリクエスト単価）
4. 切り上げの影響があるため、逆算値は概算である旨を添える

この比が対策の優先順位を決める。単価差が大きいほど
「MISS/PASS を HIT に変える」施策の効果が大きく、逆にキャッシュ済みリクエストが
支配的なら「そもそもリクエスト数を減らす」しか効かない。

## 増加要因の切り分け

`cost_monthly` の系列から、費目別に「いつから増えたか」を出す。

1. **前年同月比・前月比を同じ日数で取る。** 進行中の月は日割りで換算するか比較から外す
2. 費目ごとの**増加額**と、増加額合計に対する**寄与率**を出す
3. **減っている費目も拾う。** 過去の最適化で急減した費目があれば、
   その施策を打ち消す提案をしていないか確認する材料になる
4. 寄与率の上位2〜3費目に絞ってエンドポイント分析（`api_analytics-list`）へ進む

## リクエスト数が増える典型的な経路

| 経路 | 説明 |
|------|------|
| コンテンツ・PV の自然増 | 全エンドポイントが一様に伸びる。異常ではない。**ベースラインとして扱う** |
| フロントのファンアウト増加 | 一覧の要素ごとに個別 API を呼ぶ設計。項目追加のたびに 1PV あたりの本数が増える |
| ポーリング・全ページ設置 | 小さなエンドポイントの件数だけが跳ねる。レスポンスサイズが極小なのが目印 |
| クローラー | 深いアーカイブまで網羅巡回するため MISS 率が高い。UA・国コードの偏りで判別 |
| ファイルを API ドメインで配信 | API リクエストとして課金される。Files ドメインへ移すと消える |
| カスタム処理からの内部呼び出し | `{api_internal}`（ネットワーク経由）は課金対象。`direct=true` や `{api_method}` は課金されない |

Smarty プラグイン別の課金有無は
[カスタム処理で呼び出したAPIの利用料](https://kuroco.app/ja/docs/faq/api-usage-fees-for-custom-processing/) を参照。

## 見積もりを書くときの規律

- **削減見込みは加算しない。** 例えば「リクエスト全体を N% 減らす対策」と
  「特定エンドポイントを削る対策」は削減対象が重なる。重なりを明示し、
  実施順による目減りを書く
- **サンプルからの外挿は根拠期間を書く。** 30分のログから月次を推定したなら、
  その旨と倍率を明記する
- **キャッシュに乗せても費用はゼロにならない。** 「キャッシュ化で解決」と書かず、
  単価差ぶんの削減額として書く
- **定額契約のサイトでは管理画面にコストチャートが表示されない。** 金額の議論をする前に
  従量課金かどうかを確認する
