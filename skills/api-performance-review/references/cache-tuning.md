`../../kuroco-docs/docs/reference-api-1.md`（`cache-clear-operation`）。

## キャッシュ状態の読み方

| `cache_status` | 意味 | 課金 |
|----------------|------|------|
| `HIT` | キャッシュから返した | キャッシュされたAPIリクエストとして課金 |
| `MISS` | キャッシュが無くオリジンに到達した | APIリクエスト（高い方）＋実行時間 |
| `PASS` | そもそもキャッシュできなかった | 同上。**何度呼んでも永久にキャッシュされない** |
| `ERROR` | キャッシュ処理中のエラー | — |

レスポンスヘッダでも確認できる: `x-cache`（HIT/MISS/PASS）、`age`（キャッシュ後の経過秒）、
`x-cache-hits`（ヒット回数）。

**HIT でも無料ではない。** 対策の効果は「単価差ぶんの削減」であって「消滅」ではない。

## レバー1: キャッシュ期間（maxage）

- エンドポイントごとに秒数で設定する（管理画面のエンドポイント設定「キャッシュ」欄）
- 最大 1 年（31557600秒）。**推奨は1日〜1週間**
- コンテンツ更新時に自動クリアされるため、長め設定でも古いデータが残り続けることは少ない
- 追加・更新・削除系のエンドポイントには設定欄が無い

**現在値の確認**: `api_uri-list` の `uri_data.cache_settings.maxage`。
**変更**: `api_uri-upsert` のスキーマに `cache_settings` は無いため MCP からは変更できない。
管理画面で行うよう案内する。

---

## レバー2: 認証方式（キャッシュ単位を決める最大の要因）

キャッシュはレスポンスヘッダの `Vary` に基づいて分割される。
基本は `Host, Accept-Encoding, Accept, Origin`。認証方式で以下が加わる。

| 認証方式 | 追加される Vary | キャッシュの共有範囲 |
|----------|----------------|---------------------|
| 静的トークン | `X-RCMS-API-ACCESS-TOKEN` | **全クライアントで共通**（同一環境なら共有） |
| 動的トークン | 同上 | **ユーザーごと**に分割 |
| Cookie 認証 | `User-Agent` と `Cookie` | **セッションごと**に分割（ボット UA には Cookie を加えない） |
| API 単位の IP 制限あり | — | **クライアント IP ごと**に分割 |
| 管理画面の IP 制限あり | — | **クライアント IP ごと**に分割 |

**認証不要のデータを Cookie 認証のエンドポイントで配っていると、キャッシュはほぼ効かない。**
静的アクセストークンへの変更が最も効果の大きい改善になることが多い。

**副作用**: セキュリティ方式を変更すると、そのAPIで発行済みのトークンはすべて無効化される。
フロント改修とセットで計画し、必ずユーザー承認を取る。
変更は `api-upsert` の `security` で可能。

## レバー3: グループ単位キャッシュ（cache_by_group）

認証つきエンドポイントでも、メンバーグループ単位でキャッシュを共有できる設定。

- **有効化できるのは `Topics::list` と `Topics::details` のみ**
- ログイン系エンドポイントでは有効化できない
- 認証がメンバーごとに変わるエンドポイントでは有効化できない（認証なし／グループ認証のみ対象）
- 現在値は `api_uri-list` の `uri_data.cache_settings.cache_by_group`

条件を満たす会員向け一覧では、ユーザー単位からグループ単位へキャッシュ粒度を粗くでき、
ヒット率が大きく改善する。

## レバー4: Stale-While-Revalidate / Stale-If-Error

- **Stale-While-Revalidate**: キャッシュ失効後も設定秒数のあいだ古いキャッシュを返し続け、
  裏で新しいキャッシュを作る。**キャッシュクリア直後のオリジン集中（MISS の山）を防ぐ**
- **Stale-If-Error**: オリジンがエラーを返したときに古いキャッシュを代わりに返す

更新頻度が高くアクセスも多いエンドポイント（一覧系）で特に効く。

---

## レバー5: キャッシュクリア範囲の設計

Kuroco はデータ更新時に自動でキャッシュをクリアする。**クリア範囲を知らずに TTL だけ伸ばしても
ヒット率は上がらない。**

| 更新操作 | クリアされる範囲 |
|----------|-----------------|
| コンテンツの作成・更新・削除・承認・並び順変更 | **同じコンテンツ定義グループ**に紐づくエンドポイント全体（`Topics::details` のみコンテンツID単位） |
| コンテンツカテゴリの更新 | 同上（`Topics::details` を除く） |
| フォームの更新・回答 | 同じフォームIDに紐づくエンドポイント |
| メンバーの追加・更新 | モデルカテゴリ「メンバー」「認証」のエンドポイント全体 |
| マスタ・タグの更新 | 該当マスタID／タグ関連のエンドポイント全体 |
| ファイル操作 | 同一フォルダに関連するキャッシュ |

**更新の多いコンテンツ定義グループがあると、無関係な一覧まで巻き込まれてクリアされる。**
対策の方向:

- 更新頻度の高いコンテンツを別のコンテンツ定義グループに分離する
- 自動クリアの対象外になるエンドポイント（`Api::request_api` 等）を使い、
  クリアのタイミングと範囲を自分で設計する
  （[カテゴリ毎にキャッシュがクリアされるリストのエンドポイント](https://kuroco.app/ja/docs/tutorials/create-an-endpoint-that-clears-the-cache-by-content-category/)）
- 任意タイミングのクリアは `{purge_cdn_cache}` プラグインを後処理に置く
- クリアされたかどうかはアプリケーションログの `purgeAPI` で確認できる

## レバー6: CORS プリフライトの削減

- 既定の `Access-Control-Max-Age` は **600秒**。延ばすとブラウザ側でプリフライト結果が
  キャッシュされ、回数が減る
- `api-upsert` の `cors.maxAge` で変更できる（**ユーザー承認必須**）
- CORS 設定を変更しても、ブラウザ側の残存キャッシュ（旧 maxAge の秒数）が切れるまで反映されない
- `Content-Type` / `X-RCMS-API-ACCESS-TOKEN` / `X-Requested-With` は常に許可されている
- カスタムヘッダを一切使わない GET は「単純リクエスト」となりプリフライトが発生しない。
  ただし認証方式の変更を伴うため、影響評価が必要（→ `diagnostics.md` レシピ7）

## レバー7: リクエストそのものを減らす

キャッシュで単価を下げるより、呼ばないほうが安い。

| 手段 | 効果と注意 |
|------|-----------|
| SSG 化 | デプロイ時のみ API を呼ぶ。**クライアントサイド取得のページは削減にならない**。デプロイ回数と PV 次第では逆効果になるため事前試算する |
| 一括取得への集約 | 詳細の個別呼び出しを一覧取得に寄せる。1回 20〜200件が目安 |
| ページ内での結果共有 | 同一データを複数コンポーネントから呼ばない |
| 内部呼び出しの見直し | `{api_internal}`（ネットワーク経由）は課金対象。`direct=true` / `{api_method}` / `{api_mng}` は課金されない。ただし連続実行は実行時間を伸ばす |
| ファイル配信ドメイン | API ドメイン経由のファイルアクセスは API リクエストとして課金。Files ドメインへ |
| 不要な呼び出しの削除 | 使われていないエンドポイント呼び出しをフロントから消す |
