# Kuroco アプリビルダー

Kurocoで動くWebアプリ・サイトを**ゼロから丸ごと**構築するためのオーケストレーションスキル。
個別の実装詳細は専門スキル（後述）に委譲し、本スキルは**進め方（フェーズ設計）と橋渡し**に集中する。

**実行環境**: Codex Sites（`chatgpt.site`）は ChatGPT の通常チャットからは操作できないため、
Kurocoの構築は **Work モード（ChatGPTのワークスペース）か Codex での実行を推奨**する。
通常チャットで進める場合の公開先は KurocoFront（`/kuroco-frontend-integration` の「公開先の決定」）。

## 基本方針: フロントエンド先行（モックファースト）

Kurocoの標準的な構築順序は「コンテンツ定義 → API → フロントエンド」だが、
**ユーザーにとっては動く画面を最初に見るのが最も分かりやすい**。そこで本スキルでは順序を逆転し、
モックデータで動くフロントエンドを最初に作って見せ、画面が確定してから
バックエンドを画面に合わせて構築する。

```
フェーズ0        フェーズ1           フェーズ2         フェーズ3      フェーズ4       フェーズ5
要件ヒアリング → モックで画面構築 → コンテンツ定義   → API作成    → 実データ接続 → 最終セキュリティ点検
（機能→Kuroco     （ユーザーが見て     ・データ投入        ・セキュリティ   ・認証接続      ・security-audit
  対応付け）        フィードバック）    （Admin MCP）       設定           ・デプロイ      ・指摘の反映
                      ↑ ここで見た目を確定してから先へ進む                    ↑ ここを飛ばして完了報告しない
```

この順序が成立する鍵は、**モックデータを最初からKuroco APIのレスポンス形（契約）で作る**こと。
画面確定後は、モック実装を実API呼び出しに差し替えるだけでよい。
契約の詳細と実装パターン: [references/mock-contract.md](references/mock-contract.md)

これは既定パターン（パターンA）であり、唯一の進め方ではない。データモデルが既に確定している場合や、フロントエンドを別チームが作る場合は別パターンに切り替える——判断基準は[0-2. 進め方パターンの決定](#0-2-進め方パターンの決定)を参照。

## 進行チェックリスト

構築開始時にこのチェックリストをコピーし、進行に合わせてチェックする:

```

- [ ] 0-1. 要件ヒアリング（目的・業務範囲、ロール、画面、データと明細、データごとの状態、添付、規模、デバイス方針、デザイン方針、デモデータ）
- [ ] 0-2. 進め方パターンの決定（A モックファースト / B バックエンド先行 / C 担当外。理由を明記）
- [ ] 0-3. 機能→Kurocoマッピング表 ＋ ロール×画面の権限マトリクス ＋ データごとのステータス遷移表の作成・ユーザー合意（状態は承認ワークフローと独自ステータス項目に振り分ける）
- [ ] 0-4. 外部システム連携パターンの決定（直接呼び出し / プロキシ / 取り込み。連携先ごとに選ぶ。連携なしも明記）
- [ ] 0-5. 認証方式**と到達経路の制限**の決定（①誰に見せるか＝認証方式 ②どこから見せるか＝IP制限/Basic認証。**2つとも書く**。以降の設計全体に波及する）
- [ ] 0-6. 接続先サイトと構築制約の確定（`whoami` で対象サイトの同定・`mcp:tools.all` 以上か・拡張項目/繰り返し/カテゴリの現行上限。不足のままフェーズ2に入ると3-1で失敗する）
- [ ] 0-7. 引き継がれた既存設定の棚卸し（**サイトは必ずコピーで作られる**ため、API定義・エンドポイント・コンテンツ定義が最初から入っている。`site.copy_from_site_key` でコピー元を確定し、流用しないものは承認を得て**先に無効化／削除**。`group_id` 100以下は対象外）
- [ ] 1-1. フレームワーク選定とプロジェクト雛形作成（パターンB/Cでは該当する場合のみ）
- [ ] 1-2. Kurocoレスポンス形のモックデータ + APIクライアント層の実装（**パターンAのみ**。パターンBは実APIを直接呼ぶため不要）
- [ ] 1-3. 画面実装 → ユーザーレビュー → フィードバック反映（確定まで繰り返し）
- [ ] 2-1. Admin MCP 接続確認（0-6で未接続だった場合はここで再確認。スコープ不足なら着手しない）
- [ ] 2-2. 確定画面から逆算したコンテンツ定義の作成
- [ ] 2-3. カテゴリ・タグ・マスタ（テーブルデータ）の設定
- [ ] 2-4. サンプルコンテンツ投入（モックと同内容だと差し替え検証が楽）
- [ ] 2-5. （必要なら）メンバー・認証、フォーム、お気に入り・コメント、承認ワークフローの設定
- [ ] 3-1. エンドポイント作成（Topics::list / details 等。0-4でプロキシ/取り込みを選んだものはカスタムSmarty処理）
- [ ] 3-2. セキュリティ設定（**0-5①の認証方式** ＋ **0-5②のAPI単位IPアドレス制限**）とCORS・キャッシュ設定、Admin MCP でのエンドポイント定義の確認
- [ ] 3-3. モック契約との突き合わせ（実キー名・カテゴリID・API ID/パスの確定、モック側の訂正。**パターンAのみ**）
- [ ] 4-1. モック→実APIへの切り替え・表示確認（パターンBは1-1〜1-3が既に実API接続のため該当なし）
- [ ] 4-2. 認証フロー・フォーム送信の接続（該当機能がある場合）
- [ ] 4-3. 公開先の確認（既定はKurocoFront。指定があればその公開先）→ デプロイ（KurocoFront: Admin MCP直接デプロイ or GitHub連携）または起動手順の提示。**0-5②でフロント側の到達経路制限を決めた場合は `kuroco_front.json` の `ip_restrictions` / `basic` をここで設定する。0-5②が「制限なし」でも、ユーザーが公開を明示するまでは非公開デフォルト（robots.txt の `Disallow: /` ＋ Basic認証/IP制限の選択）を適用する**（`/kuroco-frontend-integration` の「非公開デフォルト」）
- [ ] 4-4. 後戻り更新: フェーズ2・3で確定した実際の値（拡張項目の実キー名と割当・カテゴリID・エンドポイントのパス）を、フェーズ1で作ったマッパー／定数ファイルに書き戻す
- [ ] 5-1. `/kuroco-security-audit` で最終点検（**本番デプロイ前**）
- [ ] 5-2. 指摘の反映（該当フェーズに戻って修正。**使わなくなったAPI／エンドポイントは無効化**。直さないものは理由と受容者を記録）
- [ ] 5-3. 通しで再監査（**全項目そろって問題ない状態を確認してから完了報告**）
```

記号は次の5種を使う。**行ごと削除しない**（誰が何をどう扱ったかが読めなくなるため）。

| 記号 | 意味 | 記入条件 |
|------|------|---------|
| `[x]` | 完了 | 成果物が出ている |
| `[~]` | 代替手段で充足 | 「前提が満たせないときの既定動作」の代替受け入れ条件を満たした（何で代替したかを併記） |
| `[!]` | 意図的に停止中 | **前提が満たせず**停止した（合意が得られない・接続できない等）。**再開条件を1行添える**。依頼者が納品の区切りを示していて単に着手していないだけの工程は `[!]` ではなく `[ ]` |
| `[-]` | 担当外 | 自分では実施しない。`（担当外: 〇〇チーム）` と担当を併記 |
| `[ ]` | 未着手 | 上記以外 |

4-4で書き戻す値（拡張項目の実キー名と割当・カテゴリID・エンドポイントのパスとAPI ID・フィルター文法）は、**集約先ファイルを最小個数に決めて、そこ以外に書かない**。フェーズ1の時点で集約先を決め、成果物にファイル名を明記する。

## 前提が満たせないときの既定動作

本スキルは、ユーザーの応答・外部接続・他スキルへの委譲を前提とする工程を持つ。**前提が満たせない環境でも停止せず、依存の種類ごとに下表の既定動作を取る**。表に無い依存に出会った場合も同じ原則を適用する ——「勝手に飛び越えない。確定できるところまで成果物を作り、確定できない箇所を明示して止める」。

| 依存の種類 | 満たせないときの既定動作 | チェックリスト記号 |
|-----------|----------------------|-----------------|
| **ユーザーへの質問**（`AskUserQuestion` が使えない） | 仮定を置いて進む。成果物に「確認事項」節を作り、各仮定と**外れた場合の影響範囲**を1行ずつ書く。**影響範囲には「設計やり直し」か「実装差し替え」かの区別を付ける**（前者だけが合意ゲートに載る。仮定が10件並ぶと、どれを先に確認すべきかが読めなくなる） | `[~]`（仮定で充足。何を仮定したかを併記） |
| **ユーザーの合意**（応答が得られない） | 仮合意として進み、**Kuroco側への書き込みを伴う操作の直前で停止する**（コンテンツ定義の作成・データ投入・エンドポイント作成・デプロイ）。読み取り操作と、自分の作業ディレクトリ内で完結する作業は続けてよい | 成果物を出した工程は `[~]`（仮合意）。**停止した書き込み工程は `[!]` ＋再開条件「本設計への合意」** |
| **Admin MCP の特定機能が動かない**（接続はできるが、あるツールが期待どおり保存しない・エラーを返す） | 接続不能とは別に扱う。**同種の最小データで1回試して切り分け**、動かないと確認できたら、要件を落とさない代替手段（別のフィールド型、管理画面での手順案内）に切り替えて前進する。代替にした箇所と、本来やりたかったことを成果物に明記する。同じ書式を何度も試し続けない | `[~]`（代替手段を併記） |
| **人によるレビュー**（画面を見てもらえない） | 次の3点すべてを代替の受け入れ条件とする: ①ビルド／静的生成が成功する ②主要ルートが生成され、応答する（一覧・詳細・エラーページ） ③要件に挙げた項目が生成物に含まれることを検査した結果。確認してほしい点を箇条書きで添える | 3点すべて満たせば `[~]`、満たせなければ `[!]` |
| **Admin MCP 接続**（未接続・認証不可） | 実行予定のツール呼び出しと入力JSONを**具体値付きで手順書に書き出して停止する** | `[!]` ＋再開条件「Admin MCP の接続／再認可」 |
| **他スキルへの委譲**（`/kuroco-*` が読めない） | 自分の知識で埋めてよいが、埋めた箇所に**「未検証」と明記**し、確認事項に回す。断定形で書かない | `[~]`（「未検証」と併記） |

**複数の依存が同時に満たせない場合は、該当する既定動作をすべて適用し、最も手前の停止点を採用する。**

**「書き込んでよい権限」と「設計への合意」は別のゲートである。** 混同すると、承認されていない設計を承認済みの権限で作ってしまう。

| ゲート | 誰が与えるか | 満たされないときの扱い |
|--------|------------|--------------------|
| **書き込み権限**（この環境に書いてよいか） | 依頼者・運用者。Admin MCP のスコープと、依頼者の明示的な許可 | 書き込まない。手順書に落として停止（上表の「Admin MCP 接続」行） |
| **設計への合意**（何を作るかが正しいか） | 要件の持ち主 | 仮合意として進み、**書き込みの直前で停止**（上表の「ユーザーの合意」行） |

**ゲートの効力範囲はここでのみ定義する。他の節（0-3など）が「合意を得てから先へ進む」と書いている場合も、意味はこの定義に従う。**

- **設計への合意は「Kurocoへの書き込み」のゲートであって、フェーズ遷移のゲートではない。** 合意が得られない環境でも、フェーズ1（モック実装＝自分の作業ディレクトリ内で完結）は進めてよい。
- ただし**依頼者が納品の区切りを明示している場合**（「まず設計を見せて」「設計だけ先に」）は、**その区切りが独立した停止点になる**。フェーズ0の成果物を提示して止まり、進行チェックリストのフェーズ1以降は `[ ]`（未着手）のまま残す。区切りが明示されていなければフェーズ1へ進んでよい。

事前に書き込み許可を与えられている場合でも、それは**設計への合意の代わりにはならない**。許可を根拠に書き込みまで進めるなら、「設計は未合意のまま実行した」ことと**後から変更が必要になる範囲**（作り直しになるコンテンツ定義・投入済みデータ）を成果物に明記する。

## 情報の出所と取得タイミング

モックやコンテンツ定義を作る時点では、まだ API が存在しない。**下表にある情報を推測で埋めてはいけない。** 出所が「常時」のものは必ず確認し、まだ取得できない時期のものはプレースホルダとして集約ファイル（4-4参照）に置く。

| 情報 | 出所 | 取得できる時期 |
|------|------|--------------|
| レスポンスの外形（`{ list, pageInfo }` / `{ details }`）、`pageInfo` のキー名、`filter` / `order` の構文、Topics の標準項目、キャッシュ単位と認証の関係 | `/kuroco-docs`（`reference-api-2.md` / `reference-api-3.md` / `reference-content-1.md`） | **常時**。モデル・オペレーションで決まる仕様で、サイトによって変わらない |
| 接続の実効スコープ・実効権限 | Admin MCP の **`whoami`** | 接続後。**フェーズ0で確認する**（0-6） |
| Admin MCP のツール名と `inputSchema` | Admin MCP の `tools/list` | 接続後 |
| 拡張項目のキー命名（`ext_1` 形式か `ext_col_01` 形式か。**サイト単位で異なる**） | Admin MCP の **`whoami`**（`site.topics_ext_key_format`） | 接続後 |
| コンテンツ構造の現行上限（拡張項目数・繰り返しグループの行数・カテゴリ数・会員拡張項目数）と、`number`／`searchable`／構造化JSONの可用性 | Admin MCP の **`whoami`**（`site.limits.*` は `{current, max}`、`site.topics_ext_features`） | 接続後。**フェーズ0で確認する**（0-6③）。設計がこの上限を超えていないかを0-3・2-2の前に数える |
| コンテンツ定義のフィールドと拡張項目の実キー名・割当 | Admin MCP の **`topics-describe`**（グループ単位の正） | フェーズ2以降 |
| カテゴリ・タグの実ID | Admin MCP（カテゴリ一覧の読み取り） | フェーズ2以降 |
| API ID、エンドポイントのパス、実際のリクエスト／レスポンス定義 | Admin MCP の **`api-export_openapi`**（`api_id` 必須、`format` は `json`/`yaml`）。OpenAPI 3.1.0 が返る | フェーズ3以降 |

プレースホルダには**未確定の種別と確認手段**を添える。ラベルだけでは受け手が検証コストを見積もれない。

| 種別 | 意味 | 確認手段 |
|------|------|---------|
| 存在未確認 | その機能・エンドポイントがあるか自体が不明 | `/kuroco-docs` / `tools/list` |
| 命名未確認 | あるはずだが正確な名前が不明 | `tools/list` の実名 |
| 形状未確認 | レスポンス／リクエストの構造が不明 | `/kuroco-docs` の該当リファレンス |
| 実値未確定 | 構造は分かるがこのサイトでの値が未定 | Admin MCP の読み取り（フェーズ2・3で確定） |
| 依頼者未提供 | Kuroco 側からは取得できず、**依頼者しか持っていない値**（社内ネットワークの出口IP・独自ドメイン・部署一覧・ロゴ・社内用語） | 依頼者に確認する。**この値が埋まらないと安全側に倒れない設定（IP制限の許可リスト・CORSの許可オリジン）は、値が確定するまで書き込み工程に進まない**——空や仮値で設定すると、締めたつもりで開いている状態になる |

停止点を**フェーズ番号ではなく行為の種類**で定義しているのは、0-2でパターンB/Cを選んで順序を入れ替えても停止位置がずれないようにするため。

## この案件でどこまで読むか（読み分け）

**本スキルは全案件で全文を読む前提ではない。** 下の条件に当てはまるなら、該当箇所を読まずに進めてよい——読む量を減らすことが目的ではなく、**当てはまらない案件で読み飛ばさないため**に条件を明示している。

| 条件 | 読まなくてよい箇所 |
|------|-----------------|
| 依頼が「まず設計を見せて」等で**フェーズ0までが納品の区切り** | フェーズ1〜5の本文（成果物にチェックリストを載せるので、項目名だけ見れば足りる）。**ただし「1-1 フレームワーク選定」の判定条件表は読む**——0-1 #14 がここを参照して確定させるため、フェーズ0の一部として扱う |
| 0-3で**承認ワークフローを使わないと判定した**（差し戻しがない・承認が要らないと明示されている） | 0-3の「状態（ステータス）の持ち方を決める」のうち、振り分け表より後（却下の扱い・申請中データの取得・合成規則）。**振り分け表と判定軸までは必ず読む** |
| 0-2で**パターンAを選んだ** | 「パターンB・Cの補足」節。**ただし同節の「新規API定義を作るか既存に相乗りするか」はパターンAでも使う**（認証方式が違うエンドポイントは同一API定義に混ぜられないため、0-5①の分割判断に必要） |
| **1レコードの中に複数行を内包するデータ（明細）がない** | 「明細（1対多）の持ち方」（feature-mapping）。**注意: 「明細がない」と「1対多の関係がない」は別**——親子が別レコードになる1対多（イベントと申込、コマと予約）は、明細ではなくリレーションの判断なので、この表は読まなくてよいが**成果物④には親子関係として書く** |
| 集計・グラフの要件が**ない** | feature-mapping の「集計・レポート・グラフ」行 |

**フェーズ0（0-1〜0-7）と「前提が満たせないときの既定動作」は、どの案件でも読み飛ばさない。**

## フェーズ0: 要件ヒアリングと設計

### 0-1. ヒアリング

`AskUserQuestion` が使える環境では選択式で確認する。使えない環境の既定動作は「前提が満たせないときの既定動作」表を参照。

**聞き方の原則は「列挙を確定させる」。** 画面・ロール・データ・状態は、自由記述の回答を待つより**こちらから叩き台の列挙を提示して差分を直してもらう**ほうが速く確定する（相手は0から書き出すより、並んだ一覧を見て「これは要らない／これが足りない」と言うほうが容易）。叩き台は[references/feature-mapping.md](references/feature-mapping.md)の「アプリ類型別のプリセット」から取る。

**`AskUserQuestion` は1問4択までなので、列挙の確認には向かない。** 列挙はテキストで叩き台を出し、選択式は二者択一の判断（デバイス方針・フレームワーク・公開方法・進め方パターン）に使う。

| # | 聞くこと | 形式 | 決まらないと詰まるもの | 小規模・単純な案件での扱い |
|---|---------|------|--------------------|----------------------|
| 1 | **アプリの目的と業務範囲**（どこからどこまでを一元管理するか） | 1〜2文 | スコープが発散し、画面・状態の列挙が終わらない | **必須** |
| 2 | **アプリの種類**（ブログ / コーポレート / 会員制サイト / 一覧+詳細型 / 社内業務システム / EC …） | 選択 | 0-2のパターン判断、プリセットの選択 | **必須** |
| 3 | **利用者の役割（ロール）の列挙**と、**ロールごとの見える範囲**（全件／自分が作成したものだけ／自部門・自拠点だけ／自分に割り当てられたものだけ） | 箇条書き | 会員グループ設計、画面の出し分け、0-5の認証方式、**0-3の権限マトリクスの条件列**（レコード単位の制限はここで聞かないと成果物で推測になる） | **必須**。ただしロールが1種なら「1種のみ・制限なし」の1行で足りる |
| 4 | **画面の列挙**（番号付き）と、**ロールごとの入口**（ログイン後・トップから最初に着地する画面）・**主要動線**（代表タスクが画面をどう渡って完了するか） | 箇条書き | エンドポイントの粒度（3-1）、ルーティング、ナビゲーション設計 | 画面の列挙は**必須**。画面が少なく動線が自明なら入口・動線は「トップのみ・動線自明」の1行に畳む |
| 5 | **扱うデータの列挙と親子関係**（1件に複数明細を持つか。明細の項目と想定行数） | 箇条書き | TopicsGroupの分割と明細の持ち方（2-2） | 明細を持たないことが依頼文から明らかなら「明細なし」の1行に畳む |
| 6 | **データごとの状態（ステータス）の列挙** | データ種別ごとに箇条書き | 状態の持ち方（0-3）、一覧の絞り込み、承認機能の要否 | **必須**（状態が「公開／非公開」だけの場合もそう書く） |
| 7 | **添付ファイルの種類と用途** | 箇条書き | `file` / `image` フィールドの数と複数添付の持ち方 | 依頼文で枚数が確定していれば畳む |
| 8 | **必要な機能**（ログイン、検索、お気に入り、コメント、問い合わせ、グラフ、変更履歴…） | 箇条書き | 0-3のマッピング表 | 依頼文にない機能は列挙せず「採用しない」と1行で閉じる |
| 9 | **想定規模**（利用者数、データ件数／年） | 数値 | ページネーション・キャッシュ・流量の設計 | 依頼文にあれば確定、なければ仮置き1行 |
| 10 | **デバイス方針**（PC中心か。モバイルで使う画面はどれか） | 選択＋対象画面 | フレームワーク選定（1-1）、レビューの確認範囲 | 画面が少なく全画面レスポンシブで足りるなら「全画面対応」の1行に畳む |
| 11 | **デザイン方針と使うUIパターン**（トーン、サイドバー、バッジ、テーブル、グラフ、タイムライン…） | 箇条書き | フェーズ1の実装指示。後出しになると画面ごと作り直しになる | 仮置きして確認事項へ（設計の骨格に波及しない） |
| 12 | **デモ／サンプルデータの要件**（代表1件は具体値まで） | 箇条書き | 2-4の投入内容、レビューの説得力 | 仮置きして確認事項へ |
| 13 | **他システムとの連携予定**（連携先とデータの向き: 取得のみ／送信のみ／双方向）と、**「連携」と意識されにくい外部サービス依存**（決済、地図、メール配信、既存の認証基盤・SSOなど） | 選択 | 0-4。無ければ「連携なし」と明記して先へ進む | 記載がなければ「連携なし・外部依存なし」と確定して畳む |
| 14 | **フレームワーク／公開方法** | 選択 | 1-1 / 4-3。指定がなければ1-1の判定条件で選ぶ | 判定条件を適用して確定（畳まない） |

**「小規模・単純な案件での扱い」列に沿って畳んでよい。ただし畳んだこと自体は成果物に書く**（「#5 明細なし（記事1件が単独で完結）」のように1行）。**黙って省略するのと、条件を満たして畳むのは別である。** 「必須」の項目は規模によらず確定させる——後で気づいたときの手戻りが非対称に大きい。

**逆に、畳める条件を満たさないのに仮置きで済ませない。** 下の「列挙の粒度が粗いまま先へ進まない」がその歯止め。

**状態（ステータス）はデータ種別ごとに分けて聞く。** 工程が連続する業務（申請→発注→検収→請求書照合など）では状態機械が1つではなく複数ある。1本の列挙に混ぜると、状態を動かす主体と状態を持つデータがずれ、後で分解し直すことになる。**状態ごとに「誰が」「何をすると」「次はどこへ」進むかまで聞く**——これがそのまま0-3のステータス遷移表とロール権限マトリクスになる。

**列挙の粒度が粗いまま先へ進まない。** 「承認機能」で止めず「何段の承認か／誰が承認するか／差し戻し先はどこか」まで詰める。ここが曖昧なまま画面を作ると、フェーズ1のレビューでやり直しになる。粒度を詰められない項目は、仮の列挙を置いて**外れた場合の影響範囲**を確認事項に1行書く（「前提が満たせないときの既定動作」表と同じ扱い）。

### 0-2. 進め方パターンの決定

0-1のヒアリングを踏まえ、A/B/Cのいずれで進めるかをここで決める。**判断結果と理由をフェーズ0の成果物に明記する。**

**まずユーザーの依頼内容・添付資料そのものを確認する。** スキーマ・カラム定義、既存DBのCSV、移行元サイトのAPIレスポンス例などが既に提示されている場合、それ自体が「データモデル確定」の根拠になる。**この場合は0-1で改めて確定度を聞く必要はない**——聞くのは、依頼内容から読み取れない場合に限る。

| 軸 | 状態 | 選択 |
|----|------|------|
| データモデルの確定度 | 未確定・画面から固めたい | → A |
| | 依頼内容に既存のデータ構造がある／ほぼ確定／定型リプレース | → B |
| フロント担当 | 自分（このセッション）が実装する | A または B |
| | 別チームが実装する | → C |

複雑さ（画面数・コンテンツ種類数・認証/決済の有無）は、A/B/Cの選択そのものには関与しない。単純なアプリでもデータモデルが未確定ならAが正しい。複雑さが効くのは選んだパターンの**中身の圧縮可否**——単純なら0-3のマッピング表を簡略形式にしてよいが、認証方式の決定（0-5）とAdmin MCPスコープ確認（0-6）は複雑さに関わらず省略しない（後で気づいたときのコストが非対称に高いため）。

| パターン | 順序 | 内容 |
|---------|------|------|
| **A モックファースト（既定）** | 0→1→2→3→4 | フェーズ1でKurocoレスポンス形のモックを作り、画面確定後にコンテンツ定義・APIを構築する |
| **B バックエンド先行** | 0→2→3→1→4 | 先にコンテンツ定義・APIを作る。フェーズ1は**モック構築ではなく実APIを直接呼ぶ**（モック契約の遵守・フェーズ4の切替手順は不要になる） |
| **C 担当外（API仕様書納品）** | 0→2→3 | フロントエンドは別チームが作る。フェーズ1・4-1/4-2は実施しない。詳細は[「フェーズが丸ごと担当外になる場合」](#フェーズが丸ごと担当外になる場合)を参照 |

ユーザーが順序に迷っていたら、「まず動く画面を見たいか、データ設計から固めたいか」を確認する。

### 0-3. 機能→Kuroco機能マッピングと、ロール・状態の設計

アプリの各機能をKurocoの標準機能に対応付ける。**カスタム実装の前に、標準機能で賄えないかを必ず確認する。**

| アプリの機能 | Kurocoの機能 | 作成するもの |
|-------------|-------------|-------------|
| データの一覧・詳細表示 | コンテンツ定義（TopicsGroup）+ Topics API | コンテンツ定義、`list`/`details` エンドポイント |
| 記事の分類・絞り込み | カテゴリ（TopicsCategory）・タグ | カテゴリ/タグ設定、`filter` クエリ |
| 選択肢マスタ（都道府県等） | テーブルデータ（CSVテーブル） | CSVテーブル + `csvtable` フィールド |
| 1件に複数明細（申請明細・商品バリエーション） | 繰り返しフィールドグループ / JSON項目 / 別コンテンツ定義＋リレーション | 想定行数で選ぶ（判断は `/kuroco-content-structure` の設計判断） |
| 多段の申請・承認（差し戻しあり） | 承認ワークフロー（Approvalflow） | ワークフロー設定 + `Topics::waiting_for_approval_list` / `accept` / `reject` エンドポイント |
| 業務工程のステータス管理 | `select` の状態項目 + `filter` | 状態項目（`searchable: true`）、一覧の絞り込みパラメータ |
| 変更履歴・監査ログ | コンテンツの変更履歴 / 独自のログ用コンテンツ定義 | `Topics::history_list` エンドポイント、または記録用コンテンツ定義＋トリガー処理（`/kuroco-server-processing`） |
| ログイン・会員登録 | メンバー + 認証（Cookie / Token） | Authentication系エンドポイント（`login_challenge`, `token`, `profile`） |
| お気に入り | Favorite | `Favorite::insert` / `delete` / `list` エンドポイント |
| コメント | Comment（Activity） | `Comment::insert` / `list` エンドポイント |
| 問い合わせ・投稿フォーム | フォーム（InquiryForm） | フォーム定義 + `InquiryMessage::send` エンドポイント |
| キーワード検索 | Topics検索（`topics_keyword` / filter） | `list` エンドポイントのパラメータ |

#### 状態（ステータス）の持ち方を決める

> **承認ワークフローを使わないと判定できた場合（下の振り分け表で「一方向に進むだけ」に該当）、この節はそこで読み終えてよい。** 以降の内容（却下の扱い・申請中データの取得・一覧の合成規則）はすべて承認ワークフローを使う案件のためのもの。

0-1で列挙した状態を、承認ワークフロー（標準機能）と独自のステータス項目に振り分ける。**ここを決めずに画面を作ると、承認まわりが全部自前実装になる。**

**振り分けは業務語彙で判断しない。「その遷移に差し戻し（前の主体へ戻す操作）が伴うか」で判定する。** 日本語の業務語彙（確認・査閲・回付・承認・決裁・チェック）はどれも承認ワークフローのフェーズに写像できてしまうため、語彙で判定すると同じ意味の言葉が案件ごとに別の機構に落ちる。

| 遷移の型 | 判定 |
|---------|------|
| 却下・差し戻しがあり、**前の主体へ戻して再提出させる**（内容の可否を判断する） | 承認ワークフローのフェーズ。多段なら段数ぶんの承認グループ |
| 一方向に進むだけ（戻す操作がない、または戻すのが「やり直し」でなく次工程の一種） | `select` の状態項目の1値 |
| 戻す操作はあるが、**戻す先が公開前の内容修正ではなく作業のやり直し**（例: 検収差し戻し → 作業中） | `select` の状態項目の1値。承認ワークフローは公開前の内容承認しか扱えない |
| **差し戻しの有無が確認できない**（依頼文に書かれておらず、ユーザーにも聞けない） | **既定は「差し戻しあり＝承認ワークフロー」に倒す。** 承認ワークフローで作ってから状態項目に落とすほうが、逆方向（状態項目で作ってから承認・差し戻し・通知を自前実装する）より安い。**確認事項に「差し戻しがないなら1フェーズ減らす／状態項目に落とす」と切替方向を書く**（切替コスト＝ワークフロー設定の削除と遷移表の修正で、設計やり直しにはならない） |
| **操作ではなく時間経過で変わる**（受付中→受付終了→開催終了、公開期間の満了） | **状態項目を作らず、日付・時刻のフィールドから導出する**（`filter` またはフロントの判定）。状態項目にすると誰かが手で切り替える運用になり、切り替え漏れが発生する。注意: **絞り込み条件に現在日時が入るエンドポイントは長期キャッシュしない**（日付境界でキャッシュが実態とずれる）。全件返してクライアント側で判定するか、キャッシュ期間を境界の粒度に合わせる。SSGの場合は日次の定期ビルドなど再生成の契機も決める |

「ライン長が確認して、そのあと課長が承認する」のように語が使い分けられている場合も、**両方に差し戻しが伴うなら2フェーズの承認ワークフロー**であり、確認側に差し戻しがない（通すだけ）なら状態項目の1値。

<!-- spec-note: SN-6 -->**第2の軸: 承認する側が「可否を判断する」だけか、「値を決める」のか。** 承認ワークフローの申請中データに対する操作は**承認・差し戻し・取り下げの3つだけで、承認者が申請内容を書き換える操作は用意されていない**。「スタッフが空き枠を見て振替先を決める」「担当者を割り当てて承認する」のように**承認と値の確定が同時に起きる業務**は、次のどれかに落とす:

| 落とし方 | 内容 | 向くケース |
|---------|------|-----------|
| **承認＋承認後の更新の2段** | `Topics::accept` で内容を確定させ、直後に `Topics::update` で決めた値（振替先・担当者）を書き込む。画面上はボタン1つに見せる | 差し戻しも必要で、決める値が1〜2項目 |
| **申請側に候補を持たせ、承認者は選ぶだけにする** | 申請フォームで候補（第1〜第3希望）を出させ、承認者は候補のどれかを選んで承認する | 候補を申請者が出せる業務 |
| **承認ワークフローを使わず状態項目にする** | 「割当待ち→割当済」を状態項目で持ち、割当操作＝`Topics::update` にする | 差し戻し（前の主体へ戻して再提出させる）が実際には不要な場合 |

**どれを採ったかは0-3の遷移表に書き、その選択が権限マトリクス（承認行の意味）と画面のアクション定義にも波及することを明記する。**

| 状態の性格 | Kurocoでの持ち方 | 注意 |
|-----------|----------------|------|
| コンテンツの**公開前承認**（下書き→申請→承認（多段）→差し戻し→反映） | **承認ワークフロー**。申請は `Topics::insert` / `update` に `approvalflow_id` を渡す。承認待ち一覧は `Topics::waiting_for_approval_list`、詳細は `waiting_for_approval_details`、承認は `Topics::accept`、差し戻しは `Topics::reject`（いずれもエンドポイントとして作成できるオペレーション） | 多段の承認グループ・承認者の指定（グループ／メンバー／カスタムメンバーフィルター）・差し戻し先の選択・取り下げ・承認者へのメール通知が設定だけで揃う。旧 `Approvalflow::review` / `list_pending` は非推奨 |
| 公開承認の**後に続く業務工程**（発注済み・一部検収・検収完了・請求書確認中・支払い保留・完了 等） | **`select` の状態項目** + 遷移ルールをフロント／カスタム処理側に持つ。一覧の絞り込みは `filter`、表示はステータスバッジ | 承認ワークフローは「公開してよいか」の承認だけを表現する機能で、工程の進行は表現できない。混ぜずに分ける |
| 単純な公開／非公開・下書きのみ | Topics標準の公開設定（`open_flg`） | 状態項目を作らない |

- **状態項目には `searchable: true` を付ける**（一覧の絞り込みで必ず使う。2-2参照）。
- 「下書き（本人だけに見える未提出の状態）」は Topics の途中保存（`Topics::draft_save` / `draft_list` / `draft_details`）で表現できる。状態項目に「下書き」を持たせるかは、**一覧・集計に下書きを出すかどうか**で決める（出すなら状態項目、出さないなら途中保存）。
- 承認ワークフローの操作は**承認・差し戻し・取り下げ**の3つ。**「却下（再申請させない終端状態）」に相当する操作はないため、必要なら状態項目側で持つ**（差し戻しは申請者に戻る操作であって終端ではない）。
- **ただし申請中のまま状態項目に「却下」を書き込むことはできない。** 新規申請はまだコンテンツとして存在せず（`Topics::update` の対象になる `topics_id` がない）、更新申請の場合に `update` が当たるのは公開中の版であって申請内容ではない。<!-- spec-note: SN-5 -->したがって却下の実現は次の2通りに限られ、**どちらを採るかを0-3で決めて遷移表に書く**:
  1. **差し戻し → 申請者が取り下げる**（取り下げが終端。申請内容は途中保存データとして残る）。一覧・集計に「却下」を出す必要がないならこれで足りる
  2. **いったん全フェーズ承認してコンテンツに反映させ、直後に状態項目を「却下」に更新する**。却下件数・却下理由を一覧や月次集計に出したい場合はこちら（承認は「内容を確定させる」操作で、可否の判断は状態項目側が持つ、という整理になる）

  **この選択は3つの成果物に波及する**: ①ステータス遷移表（終端の表現）②権限マトリクス（選択肢2では「承認」行が却下も含む意味になる）③画面のアクション定義（ボタンが「承認／差し戻し」か「承認して進める／修理不要として終了」か）。遷移表だけ直して他を放置しない。
- **承認完了時に工程ステータスへ何を入れるかは、状態項目の「初期値」で表現する。** 全フェーズ承認された瞬間に申請内容がコンテンツへ反映されるので、状態項目の初期値を工程の先頭（「未割当」「割当待ち」など）にしておけば、その値で反映される。**承認完了を検知して状態項目を書き込むトリガー処理は書かない**——それが「承認ワークフローと状態項目の同期処理を自前で書く」ことそのものになる。
- **申請中データは `Topics::list` から取れない。** 承認ワークフローの申請中データは公開済みコンテンツとは別系統で、`Topics::list` には承認状態のパラメータもレスポンス項目も無い。申請中の一覧は `Topics::waiting_for_approval_list`（`get_workflow_info` を有効にするとワークフロー情報がレスポンスに付く）、詳細は `waiting_for_approval_details` で取る。**承認が全フェーズ完了した時点で申請内容がコンテンツに反映され、`list` に現れる。**
- **状態の系統ごとに「保存場所 → 取得オペレーション → フロントの一覧に出せるか」を数え上げてから合成規則を書く。** 合成の本数は2本に固定ではない:

  <!-- spec-note: SN-4 — 「差し戻された申請」の行の実機確認 -->
  | 系統 | 保存場所 | 取得オペレーション | 一覧への出し方 |
  |------|---------|------------------|--------------|
  | 承認完了後（状態項目を持つ） | コンテンツ本体 | `Topics::list` / `details` | そのまま出せる。バッジは状態項目の値 |
  | 申請中（承認待ち・多段の途中） | 承認ワークフローの申請中領域 | `Topics::waiting_for_approval_list` / `waiting_for_approval_details`（`get_workflow_info` でフェーズ情報が付く） | 出せる。バッジはフェーズ名 |
  | 未提出の下書き | 途中保存データ | `Topics::draft_list` / `draft_details` | 出せる。**一覧・集計に出すかは要件で決める**（出さないなら途中保存のまま放置してよい） |
  | **取り下げられた申請** | **途中保存データとして残る**（公式に明記あり） | `Topics::draft_list` | 「再提出できる下書き」として扱える |
  | 差し戻された申請 | ワークフロー内に残り、差し戻し先（申請者／中間フェーズ／別ワークフロー）へ移る。**取り下げと違い「途中保存データになる」とは記載されていない** | `waiting_for_approval_list` 側で見える前提で設計し、**この1点だけフェーズ2で実機確認する**（見えなければ差し戻し通知メールで再提出を促す設計に落とし、状態項目に二重持ちはしない） | 実機確認の結果次第 |

- したがって**一覧画面で「承認待ち」と業務工程を1つのバッジに見せるなら、`list` と `waiting_for_approval_list` の2本を呼んで合成する**必要がある。逆に、承認操作を管理画面に閉じてフロントには公開済みデータだけ見せる設計なら合成は不要で、その場合は成果物に「合成不要」と理由を1行書けばよい（不要な合成規則を書いて設計を膨らませない）。この合成規則（どちらを優先するか・承認中のレコードを一覧に混ぜるか・件数バッジをどう数えるか）はフェーズ0で決める。**決めずにフェーズ1へ行くと、承認状態を状態項目にも二重に持たせる設計に倒れ、承認ワークフローと状態項目の同期処理を自前で書くことになる。**
- 承認ワークフローを使う場合、権限設定の「要承認」は**ユーザー種別が「編集ユーザー」のグループにしか表示されない**。申請者・承認者のグループは編集ユーザー種別で設計することになるため、**業務アプリで管理画面を見せたくないなら「管理画面利用不可」を併用する**（グループ設計の深掘りは `/kuroco-auth-design`、監査観点は `/kuroco-security-audit` D6・D7）。

#### ロール×画面の権限マトリクスを作る

0-1で列挙したロールを列、画面（または操作）を行にして、閲覧／作成／更新／承認の可否を埋める。これがないと、エンドポイントの閲覧制限（0-5・3-2）とフロントの画面出し分けが場当たりになる。

**行が「画面」だけでは足りない。** 「自分の申請だけ見える」「自部門の分だけ見える」のようなレコード単位の制限は画面単位で表現できないので、該当行に条件を書き添える（スコープ設計の深掘りは `/kuroco-auth-design`）。

**条件を書いたら、その隣に「実現機構」を書く。** レコードスコープには3つの型があり、**同じ見た目の1行でも実装コストが桁違い**になる。機構を書かないと、合意の時点でその差が見えない。

<!-- spec-note: SN-1 — 所有型・割当型の行の `my_own_list` / `self_only` の使い分けの説明 -->
| 型 | 条件の例 | 実現機構 | コスト |
|----|---------|---------|-------|
| **所有型**（自分が作成した） | 自分が出した申請だけ／自分の予約だけ | **`Topics::list` / `details` では `my_own_list`**（「自分の所有コンテンツで絞り込む」パラメータ）。**`self_only` は別物で、`draft_list`／`draft_save`／`waiting_for_approval_list`／`waiting_for_approval_details` などのパラメータ、および `relation` 型フィールドのプロパティとして存在する**（コンテンツ一覧の絞り込みには使えない） | パラメータ1つ。標準機能 |
| **属性型**（自分の所属と一致する） | 自部門だけ／自拠点だけ／自教室だけ | カテゴリ単位のグループ閲覧制限（分類が固定・少数なら単純）、または会員拡張項目＋MemberCustomSearchAuth | 設定のみ。標準機能の範囲は `/kuroco-auth-design` 4. で確認 |
| **割当型**（他者から自分に割り当てられた） | 自分に割り当てられた作業だけ／自分が担当するコマだけ | **`my_own_list` も `self_only` も作成者判定なので使えない**（割り当てられた側は作成者ではない）。最小の代替実装は**エンドポイント側で `filter` にログイン会員IDを固定条件として差し込むカスタム処理**（`/kuroco-server-processing`）。**フロント側の絞り込みで代替してはいけない**——レスポンスに他人のレコードが載り、DevToolsから読めてしまう | **カスタム実装。工数として明示する** |

**割当型は業務アプリで最も頻出するのに、標準機能に素直な受け皿がない。** 「担当者だけが見える／操作できる」が要件にあるなら、その行を**要カスタムとして権限マトリクスに残す**（要件を落とさず、工数を見えるようにする）。同様に「同じグループのメンバーの投稿だけ見せる」も標準機能ではない。

**成果物**: 次の4点を提示し、ユーザーの合意を得てから先へ進む。テンプレートは[references/feature-mapping.md](references/feature-mapping.md)。合意を得られない環境での扱いは「前提が満たせないときの既定動作」表を参照。

1. 画面 ↔ 使用エンドポイント ↔ コンテンツ定義・フィールド の対応表。**各行に「実装主体」（フロント実装／Kuroco管理画面）を書く**——**書き手が少人数で管理画面を使える場合、投稿・編集・承認の画面をフロントに作らない選択を先に検討する**。作らなければエンドポイント（`insert`/`update`/承認系/認証系）と認証設計がまとめて不要になり、規模の小さい案件では設計が半分以下になる。その場合も「執筆は管理画面で行う」と1行書き、設計から執筆手段が抜けたように見えないようにする
2. ロール×画面（＋レコード単位の条件）の権限マトリクス
3. データごとのステータス遷移表（状態・遷移させるロール・トリガーとなる操作・次の状態・持ち方）と、**一覧に出すステータス表示の定義**。承認ワークフローと状態項目の両方を使い、かつ**申請中のデータをフロントの一覧に出す**場合は、`list` と `waiting_for_approval_list` の合成規則を書く。**該当しない場合（承認を管理画面に閉じてフロントは公開済みだけ見せる／承認ワークフローを使わない）は「合成不要」＋理由1行でよい**
4. データモデルの親子関係（明細の有無と想定行数。持ち方の判断は `/kuroco-content-structure` の設計判断に渡す）

**4点はいずれも、該当しない場合は「該当なし＋理由1行」で満たしたことにする。空の表を出さない。** 軽いアプリでは実際に該当しないものが出る——例: 明細を持たないアプリの4は「明細なし（記事1件が単独で完結）」の1行、ロールが1種類しかないアプリの2は「ロール1種のため出し分けなし」の1行。**逃げ道を使ったこと自体を書く**のが目的で、省略して黙るのとは違う。

### 0-4. 外部システム連携パターンの決定

0-1で連携予定を確認済みなら、連携先ごとにどのパターンを取るか決める。**連携先が複数あれば、それぞれ個別に選んでよい**（1アプリ内でパターンが混在してよい）。連携がない場合は「連携なし」と成果物に明記して次に進む。

| パターン | 構成 | 向くケース | 実装の参照先 |
|---------|------|-----------|-------------|
| **直接呼び出し** | フロントエンドが外部システムのAPIを直接呼ぶ。Kurocoは関与しない | 外部API側がCORSを許可済み・鍵をフロントに置いてよい・リアルタイム性を最優先したい | フロント側のみ（Kuroco側の作業なし） |
| **プロキシ（Kuroco経由）** | フロントはKurocoのカスタムエンドポイントを呼び、そのSmartyテンプレート内で **`{api}`** プラグインから外部APIを呼んで結果を返す | 外部APIキーを隠したい、認証・CORS・レート制限をKuroco側に一本化したい、レスポンスを加工・合成したい | `/kuroco-server-processing`（`{api}` プラグイン） |
| **取り込み** | 構造化データ（外部API）は**バッチ処理**が定期的に`{api}`で取得し`{api_internal}`でTopicsへ挿入。非構造データ（Webページ・ファイル）は**スパイダー**が巡回して取り込む。即時反映が要る単発イベントは**Webhook/トリガーメールアドレス**で受ける。いずれも標準のTopics APIで提供する | 更新頻度が低い、Kurocoの標準機能（キャッシュ・検索・カテゴリ・多言語）に外部データも乗せたい、外部システムが不安定・低速 | `/kuroco-server-processing`（バッチ処理・スパイダー・トリガー） |

判断基準（正は `/kuroco-server-processing` の「外部システム連携の方式設計」。以下はその要約）:
- **鍵を秘匿する必要があるか** → あるならプロキシか取り込み。直接呼び出しはフロントのJSから鍵が読めるため、非公開の鍵には使えない
- **リアルタイム性が必要か** → 必要ならプロキシ、許容できるなら取り込み
- **Kurocoの標準機能（検索・カテゴリ・キャッシュ・多言語）に外部データも乗せたいか** → 乗せたいなら取り込み
- **スパイダーは構造化APIのポーリングには向かない**（Webページ・ファイルの巡回取り込み用）。構造化APIを定期取得するなら取り込みでもバッチ処理を使う

選んだパターンは0-3のマッピング表に連携先ごとに追記する。プロキシ・取り込みを選んだ場合、フェーズ3のエンドポイント作成は標準の`Topics::list`/`details`ではなくカスタムSmarty処理が必要になる（3-1参照）。認証方式・レート制限・タイムアウト・秘密情報の保管場所など、連携先ごとの深い設計判断は `/kuroco-server-processing` の「外部システム連携の方式設計」（`references/integration-design.md`）を使う。

### 0-5. 認証方式と到達経路の制限の決定

**設定作業はフェーズ3だが、決定はここで行う。** 必要な入力（会員機能の有無・フロントとAPIのドメイン構成）は0-1で揃っており、この判断はエンドポイント設計・CORS・フロントの実装方式すべてに波及するため、後に回すと手戻りになる。バックエンド先行に切り替えた場合も同じ。

**この工程の決定は2つある。混ぜない。**

| 決定 | 問い | 手段 |
|------|------|------|
| **① 認証方式**（本人性） | **誰に**見せるか。利用者を識別する必要があるか | 認証なし / Cookie認証 / 動的アクセストークン / 静的アクセストークン |
| **② 到達経路の制限**（ネットワーク境界） | **どこから**アクセスできるか | APIのIPアドレス制限 / KurocoFront配信のIP制限・Basic認証 / 制限なし |

**「社内からだけ見せたい」「関係者だけに見せたい」は①では表現できない要件で、②に落ちる。** ①だけ決めて先へ進むと、社内限定の要件が「会員登録して全社員にアカウントを配る」設計に化ける。**②は「制限なし」であっても成果物に明記する**（決めた結果として制限がないのか、考えていないのかが区別できなくなるため）。

#### ① 認証方式

| 条件 | 認証方式 |
|------|---------|
| 公開コンテンツのみ（会員機能なし） | 認証なし + キャッシュ |
| 会員機能あり + フロントとAPIを同一親ドメインに揃えられる | Cookie認証 |
| 会員機能あり + クロスドメインのSPA（ドメインを揃えられない／Safariの制限を避けたい） | **動的アクセストークン認証**（`X-RCMS-API-ACCESS-TOKEN` ヘッダー） |
| サーバ間通信・公開情報の提供のみ | 静的アクセストークン。**会員情報など非公開データには使わない**（トークン文字列は通信やJSから外部閲覧可能） |

**tips: 公開範囲・デフォルト権限を先に設計してから認証方式を選ぶ**

最終的にはフェーズ5で `/kuroco-security-audit` で設定を棚卸しするが、その手前でこの観点を潰しておくと手戻りが減る。APIは基本的にすべてのデータの出入り口になるため、**「このデータは公開されてよい内容か」をコンテンツ・エンドポイント単位で先に決めてから**、上表の認証方式・APIセキュリティ方式（`none` / 静的トークン / 動的トークン / Cookie）を選ぶ。

- セキュリティ方式が `none`（認証なし）のエンドポイントは、そこを通るデータ全てが公開情報であることを確認する。
- **特権付き静的トークン（`privileged_static_token`）は無期限のログイン済み資格情報に相当し、漏洩時の影響が通常の静的トークンより大きい。本当に必要な用途に限定し、安易に使わない**（詳細は `/kuroco-security-audit` チェックリストA2b）。
- **承認ワークフローで会員自身に申請させる場合は、下の既定②を適用できない。** 「要承認」設定は編集ユーザー種別のグループにしか表示されないため、申請者グループは編集ユーザー種別で作る必要がある。この場合は①（対象のコンテンツ定義に限定した作成権限）＋**「管理画面利用不可」**で組み、**範囲限定が実際に効くかをフェーズ2で実機確認する**。承認ワークフローを使わない投稿・申込・予約では②が既定。
- **会員自身がレコードを作る要件（投稿・申込・予約）がある場合、初期グループの権限は次の2択で設計する。** ①対象のコンテンツ定義に限定した作成権限を初期グループに与える（範囲を限定できるかはフェーズ2で実機確認する） ②初期グループには編集系権限を与えず、**公開エンドポイントのカスタム処理（`{api_internal}` で内部エンドポイントを呼ぶ）でレコードを作る**（`/kuroco-server-processing`）。**既定は②**——会員に編集系権限を与えると、対象外のコンテンツにも書けないかの検証が毎回必要になるため。
- **会員登録時にデフォルトで割り当てられるグループの権限は、セキュリティ上とくに重要な確認ポイント。** 管理画面の利用要否・コンテンツ更新権限の要否を先に洗い出し、不要なら「管理画面利用不可」にする。コンテンツの更新をさせない会員サイトであれば、初期グループは編集系権限を持たない「ログインユーザー」相当にとどめる（詳細は `/kuroco-auth-design` 2.、監査観点は `/kuroco-security-audit` チェックリストD6）。

サードパーティCookie問題の回避策は `/kuroco-frontend-integration`、設定の詳細は `/kuroco-api-content` を参照。**決定結果はフェーズ0の成果物に明記する。**

#### ② 到達経路の制限

| 要件 | 手段 | 設定場所 |
|------|------|---------|
| 社内ネットワーク（オフィス・VPN）からだけ**APIを叩ける**ようにする | **API単位のIPアドレス制限** | 管理画面 [API]→[セキュリティ]→[IPアドレス制限]、または Admin MCP のAPI設定。指定形式は個別IP・CIDR（`192.0.2.0/24`）・範囲（`192.0.2.1-192.0.2.2`）。複数拠点は [環境設定]→[定数] に `IPSETS_*` を作り `[[IPSETS_OFFICE]]` で参照する |
| 同じ範囲から**フロントの画面も**開けないようにする | **KurocoFront の `ip_restrictions`**（必要なら `basic` でBasic認証） | `kuroco_front.json`。Basic認証のパスワードは平文で入るので公開リポジトリに置かない |
| 制限しない（公開サイト） | なし | 「制限なし」と成果物に明記 |

- **API側だけ塞いでフロントを開けたままにしない。** データはブロックされても、画面の構造・存在・ビルド成果物は外部から読める。**社内限定の要件なら両方を同じ範囲で塞ぐ**（詳細は `/kuroco-api-content` のIPアドレス制限、`/kuroco-frontend-integration` の `kuroco_front.json`）。
- **API単位のIPアドレス制限を設定すると、キャッシュがクライアントIPごとに生成される。** 許可IPの数だけキャッシュが分割されるため、拠点やVPNの出口IPが多いとヒット率が落ちる（単一のNAT出口なら実質1本）。認証なし＋キャッシュで運用する設計では、この副作用を成果物に書く。
- 閲覧制限は上位から評価される: **API単位のIP制限 → エンドポイント単位 → コンテンツ定義単位 → カテゴリ単位 → 個別コンテンツ**。上位で拒否されると下位の設定に関わらず拒否される。
- **IP制限は本人性の代わりにはならない。** 同じネットワークにいる全員が同じデータを見られるため、「誰が見たか」「その人のデータだけ見せる」が必要なら①側で会員認証を選ぶ。
- **②が「制限なし」（公開サイト）でも、公開はユーザーの明示があってから。** それまでのデプロイは非公開デフォルト（robots.txt の `Disallow: /` ＋ Basic認証/IP制限）で行う（4-3で適用。詳細は `/kuroco-frontend-integration` の「非公開デフォルト」）。

会員グループ設計・登録フロー・コンテンツアクセス制限のスコープ・パスワードポリシー/2要素認証・代理ログインなど、この4択より踏み込んだ設計が必要な場合は `/kuroco-auth-design` を使う。

### 0-6. 接続先サイトと構築制約の確定（Admin MCP）

**書き込みはフェーズ2以降だが、確認はここで行う。** スコープ不足は
**コンテンツ定義の作成（2-2）までは成功し、エンドポイント作成（3-1）で初めて失敗する**ためで、
気づいた時点では中途半端に作られたコンテンツ定義が残っている。

**この工程で確定させるのはスコープだけではない。** `whoami` の1回の呼び出しで、以降の設計判断を縛る値がまとめて返る。**返った値を読み落とすと、フェーズ0で決めた設計がフェーズ2で作れないことが判明する。**

#### ① まず対象サイトを確定する（スコープ確認より前）

**接続が1つである保証はない。** Admin MCP サーバーが複数つながっている環境では、`whoami` を呼べたことは「構築先の情報が取れた」ことを意味しない。次の順で進める:

1. 接続候補を列挙する（複数あれば、それぞれの `whoami` の `site.site_key` / `env` を並べる）
2. **対象を1つ確定し、その根拠を成果物に書く**（依頼で指定された／唯一の接続だった／ユーザーに確認した）
3. 確定した対象から値を取る

**ユーザーに確認できず、候補が複数残る場合の決定順序**（上から順に適用し、決まった時点で止める）:

1. **要件を満たせない候補を落とす。** 判定材料は `permissions.granted` / `permissions.denied` と `permissions.connection.scope`。**必要権限は0-3・0-4で選んだ機構から逆算する**——会員グループを作るなら `group` の書き込み、集計バッチを作るなら `batch` の書き込み、エンドポイント作成なら `mcp:tools.all` 以上（会員グループ・汎用Smartyバッチの作成は `mcp:admin` が必要）。**0-3がまだ暫定なら暫定のまま逆算してよい**（後で機構が変わったらこの判定をやり直す）
2. **`env` が `prod` でない候補を優先する**（本番への誤爆を避ける）。**候補が全て `prod` ならこの段は飛ばす**——そのうえで採用した候補が `prod` なら、**書き込み許可が明示されていても `site-backup` の完了（`site_backup-list` で `ready=true`）を書き込みの前提条件にする**。確認事項にもその旨を書く
3. 依頼の文脈に一致する候補を優先する（サイトキー・接続名が対象プロジェクト名と一致する等）
4. それでも残るなら**先頭の候補を暫定採用**し、確認事項に「候補一覧・選んだ根拠・外れた場合の影響範囲」を書く

決めた結果と根拠を成果物に書けば、後から差し替える判断材料が残る。

依頼にサイトの指定がなく候補が複数ある、または `site.env` が `prod`（本番）だった場合は、**そのことを確認事項に1行書く**（外れた場合の影響範囲＝下表の制約値がすべて変わり、コンテンツ定義の分割・分類の持ち方・明細の持ち方を再判定することになる）。暫定で1つ選んで先へ進んでよいが、**フェーズ2の書き込み前に必ず確定させる**。

#### ② スコープを確認する

`permissions.connection.scope` を確認する:

| 実効スコープ | 本スキルでの扱い |
|------------|----------------|
| `mcp:admin` | 制約なし |
| `mcp:tools.all` | 通常の構築は可能。会員グループ・汎用Smartyバッチの作成変更削除、スーパーユーザーグループの付与、特権付き静的トークンの発行だけ不可 |
| `mcp:tools.write` 以下 | **エンドポイントを作成できない。** 構築に着手しない |

不足している場合は、**推測でツールを呼んで失敗を確かめない。**
`whoami` の `permissions.connection.available_scopes` を提示し、必要なレベルでの再認可を依頼する。
`mcp:admin` はスーパーユーザーしか取得できないため、相手が該当しないなら `mcp:tools.all` を案内する。

未接続の場合は「前提が満たせないときの既定動作」に従い、**必要なスコープを成果物に明記**したうえで
フェーズ1（モック構築）を進める。フェーズ2の着手前に必ず解消する。

スコープの内訳と権限モジュールの対応は `/kuroco-admin-mcp` を参照。

#### ③ 同じ `whoami` から構築制約を読み、成果物に転記する

**スコープだけ見て次に進まない。** 下表の値は0-3・2-2の設計判断を直接縛る。**読まずに設計すると、フェーズ2の作成時に「上限で作れない」「キー名が想定と違う」ことが判明する。**

<!-- spec-note: SN-2 — topics_contents_type_cnt 行の否定形の注記 / SN-3 — can_update_ip_restrictions 行の対象範囲の注記 -->
| 読むフィールド | 何が決まるか | 転記先 |
|--------------|------------|-------|

| `site.copy_from_site_key` | **このサイトのコピー元**（Kurocoのサイトは必ず何かのコピーとして作られる）。0-7 で引き継がれた設定をどう扱うかの既定が決まる。**返らない環境もある**ので、無い場合は「不明」として 0-7 のフォールバックに回す | 0-7の棚卸し表 |

### 0-7. 引き継がれた既存設定の棚卸しと無効化

**Kurocoのサイトは必ず何かのサイト（テンプレートサイト／既存サイトの複製）のコピーとして作られる。**
どの新規サイトにもコピー元のAPI定義・エンドポイント・コンテンツ定義・カテゴリ・会員グループが最初から
入っており、「まだ何も作っていないから空」は成り立たない。**流用しないものは構築を始める前に止める。**
フェーズ5まで残すと、自分が作ったものとコピー元由来の区別が付かず、コピー元の認証方式・CORS・トークンを
引き継いだエンドポイントが公開状態のまま残る。

<!-- spec-note: SN-7 — 手順3の `Default` 名フォールバックと、下表の「返らない・不明」行 -->
#### 手順

1. **0-6① で確定した対象サイトに繋がっていることを確認する。** コピー元（稼働中の本番かもしれない）で無効化すると実害が出る
2. **`whoami` の `site.copy_from_site_key` でコピー元を確定する**（返らない環境では「不明」。推測で埋めない）→ 下表の既定を適用する
3. `api-list` → `api_uri-list`、コンテンツ定義の一覧（**ツール名は `tools/list` の実名で確認**）を取り、「流用する／しない／判断保留」に振り分けて**ユーザーに提示する**。用途が読めないものは保留に置く（消すより残すほうが安全）。**名前が `Default` のままなら**テンプレート由来の可能性が高く、対応する用途が無ければ保留にせず「流用しない」でよい
4. 承認後に実行し、振り分け結果（理由付き）を成果物に書く。フェーズ5の監査で「A7はここで処理済み」と照合できる

#### コピー元ごとの既定の扱い

| `copy_from_site_key` | 既定の扱い |
|---------------------|-----------|
| `nuxt-auth-template` | **コンテンツ定義 `id=1` と API `id=1` は上書きして流用する**（新規に作らない）。**API `id=1` 配下の既存エンドポイントは削除**してから 3-1 で作り直す |
| 上記以外 | 手順3で振り分ける |
| 返らない・不明 | 同上。コピー元が特定できない旨を成果物に1行書く |

**表に無いコピー元では既定を推測しない。** 一覧を出してユーザーに振り分けを確認する。

#### 注意

- **無効化・削除はKurocoへの書き込み。** [ゲートの定義](#前提が満たせないときの既定動作)どおり承認を取る（得られなければ棚卸し表だけ出して `[!]`、再開条件「対象への承認」）。**既定は削除ではなく無効化**——`Default` 名などテンプレート由来と判断でき中身も空なら削除してよい。`env` が `prod` なら `site-backup` 完了を前提条件にする
- **無効化するとそのAPIの発行済みトークンも削除される。** 引き継いだトークンの利用者がいないかを実績（`api_uri-list` の直近8日間、`api_analytics-list`）で確かめてから実行する。`Default` という名前は手がかりであって証拠ではない（改名して使っている／`Default` のまま本番で使っている場合がある）
- **データが入っているコンテンツ定義は「流用しないが残置」を選んでよい**（止めると参照が壊れる）。成果物に「未使用（残置）」と書き、フェーズ5でも同じ扱いを引き継ぐ
- **`group_id` 100以下の会員グループはKurocoの基本グループ。** `group_id = 1`（Administrator）は標準機能が依存するので触らない。`2`（Editor）以降は不要なら削除してよいが、要件に無いだけで積極的に消す必要はない
- トークン・シークレットのコピー元由来分は構築の範囲外。気づいた分は運用者への申し送りに書く（監査観点は `/kuroco-security-audit` の D・E カテゴリ）

## フェーズ1: モックでフロントエンド構築

> **パターンAの内容。** パターンB（バックエンド先行）では本フェーズを「実APIを直接呼ぶ」形に読み替える——モック契約の遵守（手順3）とフェーズ4での切替（4-1）は不要になる。フィールド逆算（手順5）の代わりに、フェーズ2・3で確定済みのフィールド・エンドポイントをそのまま使う。パターンCでは自分は本フェーズを実施しない。

**目的: 最短で「動く見た目」をユーザーに見せ、画面を確定させる。**

1. **フレームワーク選定とプロジェクト雛形**: ユーザー指定がなければアプリの種類で選ぶ

   **判定はアプリの類型名ではなく、下の条件で行う**（類型名で決めると「社内限定のブログ」のように類型は同じでも条件が逆のケースで必ず誤選択になる）。上から順に見て、最初に当たった行を採る:

   | 判定条件 | 選ぶもの | 理由 |
   |---------|---------|------|
   | **SSR / ISR が要るか**（ページ数が多くSSGのビルドが回らない／更新頻度が高くビルド待ちが許容できない）。**SEO・OGPが動機ならSSGで足りるので「不要」。会員制・認証必須の画面も「不要」**——サーバー側fetchにセッションCookieが乗らずSSRの利点が出ない | 要るなら **Next.js / Nuxt のSSR構成 + Vercel等**。KurocoFrontは静的ホスティングなので配信できない | 公開先がKurocoFrontから外れる唯一の技術的理由。切り分けは `/kuroco-frontend-integration` の「SSR/ISRが本当に必要かの切り分け」に従う |
   | 検索エンジンにクロールさせる必要があるか（**公開サイトで流入が要る**か。社内限定・認証必須・IP制限下ならクロールされないので「不要」） | 必要なら **Nuxt 3（`nuxt generate` でSSG）** | 静的HTMLが必須。公式ドキュメント・チュートリアルもNuxt中心で根拠を引きやすい |
   | 上がSSGになる場合、**コンテンツ追加のたびに再ビルド・再デプロイできる運用か**（更新するのが非エンジニアで、更新頻度が高いなら不可） | **クロールが明示要件なら SSG を維持し、デプロイを自動化して両立させる**（コンテンツ更新トリガー → GitHub Actions → KurocoFront への自動デプロイ。日付で表示が変わる画面は日次の定期ビルドも足す）。クロールが「あれば嬉しい」程度なら **Vite + Vue 3（SPA）** に落とす | SSGは記事1本の追加ごとに再ビルドが必要で、運用者がデプロイできないと「公開したのに出ない」が定常化する。**ただし SPA に落とすと1行目の要件（検索流入）が失われる——明示要件を後続行で打ち消してはいけない**。自動デプロイの実装は `/kuroco-server-processing`（トリガー） |
   | クロールが不要（会員向けツール・ダッシュボード・社内システム・認証必須の画面が中心） | **Vite + Vue 3（SPA）** | 最小構成でSSRの落とし穴がなく、全fetchがブラウザ発なので認証が素直。`vite build` → `dist/` をKurocoFrontのrewritesでそのまま配信できる |
   | チームがReact前提 | Vite + React（SPA）/ Next.js（static export） | 上の条件の答えを保ったままReact系に置き換える（クロール必要なら static export、不要ならSPA）。**Next.jsのstatic exportでは `cookies()` / Server Actions / ISR が使えない**——制約と対処は `/kuroco-frontend-integration` を参照 |

   構成は `/kuroco-frontend-integration` のプロジェクト構成に従う。SSR/SSGでのデータ取得にはサーバー側fetchにセッションCookieが乗らない落とし穴があるため、認証付きコンテンツを扱う画面はSPA（クライアント側fetch）に寄せる

   0-1でデバイス方針を絞った場合（例: PC中心で、モバイルは申請確認と承認だけ）、**モバイル対応の対象画面をレビュー時に明示する**。全画面をモバイル最適化しない——対象外の画面に工数を払うと、確定させたい画面のレビューが遅れる
2. **APIクライアント層を1枚挟む**: UIコンポーネントから直接fetchせず、`composables/useKurocoApi.ts`（Nuxt）や `lib/kuroco/client.ts`（Next）を経由させる。モック/実APIは環境変数で切り替え
3. **モックデータはKurocoレスポンス形で作る**: 一覧は `{ list: [...], pageInfo: {...} }`、詳細は `{ details: {...} }`。拡張項目は生のキー名（`ext_1` / `ext_col_01`）のままにせず、クライアント層のマッパーでアプリ用の型に変換する（[references/mock-contract.md](references/mock-contract.md) の契約に従う）
   - **中身は0-1で聞いたデモデータ要件どおりに作る。** 代表1件を具体値（金額・件数・添付の枚数など）まで指定されている場合はその値を使う。レビューの説得力が上がるうえ、2-4で投入するサンプルコンテンツの内容がここで確定する
   - **状態（ステータス）は全パターンを1件以上含める。** 一覧のバッジ・絞り込み・遷移ボタンの出し分けは、その状態のデータが無いと確認できない
4. **画面実装 → レビュー**: 開発サーバーを起動して見せる（またはスクリーンショット）。フィードバックを反映し、**画面が確定するまでフェーズ2に進まない**。人が画面を見られない環境での代替受け入れ条件は「前提が満たせないときの既定動作」表を参照
5. **フィールド逆算**: 確定した画面で使っている項目（タイトル・画像・日付・カテゴリ…）を洗い出し、フェーズ2のコンテンツ定義のフィールド一覧に変換する。**状態項目・明細の行構造・添付の種類ごとのフィールド・ロール判定に使う項目（申請者・所属部門など）も逆算対象に含める**——画面のバッジや出し分けに使っているのに、フィールドとして拾い忘れやすい

> **なぜ画面確定を待つか**: コンテンツ定義の変更（フィールド追加・型変更）は作成よりコストが高く、
> 投入済みデータの修正も伴う。画面から必要フィールドを確定させてから一度で作るほうが速い。

## フェーズ2: バックエンド構築（Admin MCP）

**書き込み操作（INSERT/UPDATE/DELETE）は必ず実行前にユーザーに確認する。**

1. **接続確認**: `whoami` ツール（Admin MCP）で認証状態を確認し、`tools/list` でツール一覧を確認。未接続なら `/kuroco-admin-mcp` の手順で接続してもらう（OAuth推奨）。接続できないまま進める場合の成果物は「前提が満たせないときの既定動作」表を参照
2. **コンテンツ定義の作成**（**0-7 で「上書きして流用する」と決めた定義は新規作成せず更新する**。`nuxt-auth-template` からのコピーなら `id=1` が対象）: まず `/kuroco-content-structure` の Part 1（設計判断）で、フェーズ1で逆算したフィールドをもとにTopicsGroupの分割・マスタデータの表現方法（CSVテーブル vs `relation`）・分類の持ち方・`ext_slug`命名を設計する。設計が確定したら同スキルの Part 2（Admin MCP での作成）に従い、JSONを構築して `topics_group-create` ツールで作成する。作成前に必ずツールの `inputSchema`（`tools/list`）を確認する。**画面の検索・絞り込みでよく使う項目には `searchable: true` を設定する**（管理画面の検索フォームに表示され、内部的に `ext_limit_item.searchable=1` として保存される。フィールド一覧は `/kuroco-content-structure` 参照）
3. **カテゴリ・タグ・マスタ**: 画面の絞り込みUIに対応するカテゴリ／タグを設定。選択肢マスタが必要ならテーブルデータ（CSVテーブル）を用意
4. **サンプルコンテンツ投入**: `topics-create` 系ツールで数件投入する。**モックデータと同じ内容**にすると、フェーズ4の差し替え検証で画面差分がないことを確認できる。複数件は並列せず1件ずつ
5. **必要に応じて**: メンバーグループ・認証設定、フォーム定義、お気に入り・コメントの有効化、承認ワークフローの作成（0-3で承認ワークフローを選んだ場合。承認グループ＝承認フェーズを段数ぶん作り、承認者をグループ／メンバー／カスタムメンバーフィルターで指定する。0-3のステータス遷移表がそのまま設定内容になる）。該当ツールが `tools/list` に見えない場合はスコープ不足の可能性（`/kuroco-admin-mcp` のチェックリスト参照）。ツールがなければ管理画面での設定手順を案内する

## フェーズ3: API作成

1. **エンドポイント作成**: 画面↔エンドポイント対応表のとおりに作成する。**0-7 で「上書きして流用する」と決めたAPI定義に作る**（`nuxt-auth-template` からのコピーなら API `id=1`。既存エンドポイントは 0-7 で削除済みの前提）
   - **エンドポイントは作成時に公開設定を明示する**（既定値に依存しない）。作成後は `api-export_openapi` で
     エンドポイントが実際に現れることを確認する
   - Admin MCP に API定義系のツールがあるか `tools/list` で確認（名前は推測せず必ず一覧で確認）
   - ツールがない場合は管理画面（[API] → 対象API → [エンドポイント追加]）の手順を、モデル・オペレーション・パスの具体値付きで案内する（手順の詳細は `/kuroco-docs` の `tutorials/configure-endpoint` を参照）
   - **0-4でプロキシ／取り込みパターンを選んだエンドポイントは、標準の`Topics::list`/`details`ではなくカスタムSmarty処理が必要。** プロキシは`{api}`プラグインで外部APIを呼んで結果を返すテンプレート、取り込みはバッチ・スパイダー・トリガーで先にTopicsへ取り込んでから通常のTopics APIで返す。実装は `/kuroco-server-processing` に従う
2. **セキュリティ設定・キャッシュ設定**: **0-5で決定した認証方式**を適用し、CORSを設定する（フロントエンドのオリジンを許可、Cookie認証なら `Allow-Credentials`）。ここで方式を決め直さない——0-5の判断表に戻る。**認証不要かつ更新頻度が低いエンドポイントは、キャッシュ期間を最低1日（86400秒）程度に設定する。** コンテンツ更新時にどの範囲のキャッシュが自動クリアされるかは `/kuroco-api-content` の「Topicsのキャッシュクリア範囲」を参照——標準のTopics API（list/details等）は自動クリアされるが、プロキシ・取り込みパターンのカスタムSmartyエンドポイントは自動クリアされない点に注意
3. **モック契約との突き合わせ**（**パターンAのみ**。パターンBはこの時点でまだフェーズ1のモックが存在しないため対象外——フェーズ1で実APIをそのまま呼ぶ）: フェーズ1で仮置きした値を実物に合わせる（拡張項目の実キー名と割当・カテゴリの実ID・API IDとパス）。差分はマッパーで隠さず、**モック側を実物に訂正する**（モックが契約の写しであることを保つため）。書き戻し先は 4-4 で決めた集約ファイル1箇所
   - **突き合わせの元は Admin MCP の `api-export_openapi` ツールで取得する。** そのAPIの OpenAPI 3.1.0 ドキュメントが返るので、モックとの照合が機械的に済む
     - 入力: `api_id`（integer、必須）、`format`（`json` \| `yaml`、既定 `json`）
     - 読み取り専用ツール（`mcp:tools.read` スコープで利用可）。書き込み権限は不要
     - 補足が要る場合のみ、コンテンツ定義・カテゴリ一覧の読み取りツールを併用する
   - レスポンスの外形（`{ list, pageInfo }` / `{ details }`）はモデル・オペレーションで決まる仕様であり、確認先は `/kuroco-docs`。エンドポイントごとに変わるものではない
   - **ブラウザ（Swagger UI・管理画面）を使う手順は取らない。** Admin MCP でも `Api::openapi_data` でも読めない情報があれば、その旨と管理画面での確認箇所をユーザーに伝えて停止する

## フェーズ4: 実データ接続と公開

1. **切り替え**: `.env` にKurocoのAPIベースURL（`https://{site_key}.g.kuroco.app`）を設定し、APIクライアント層をモックから実装に切り替える。UIコンポーネントは変更しないのが理想
2. **表示確認**: モック時と同じ画面が実データで表示されることを確認。差分が出たらレスポンス形の想定違いなので、クライアント層のマッパーで吸収する
3. **認証・フォーム接続**: ログイン／会員登録は `/kuroco-frontend-integration` の実装パターンに従う（サードパーティCookie問題に注意）
4. **公開先の確認**: 既定はKurocoFront。ユーザーがVercel / Netlify / Codex Sites などを指定した場合だけ変える。判断ルールと、KurocoFront以外を選んだときの確認軸（CORS許可オリジン、Cookieのドメイン、独自ドメイン、公開URLの恒久性）は `/kuroco-frontend-integration` の「公開先の決定」に従う
5. **デプロイ**: KurocoFrontの場合は2通り（詳細手順・`kuroco_front.json` の設定は `/kuroco-frontend-integration` 参照）
   - **非公開デフォルト**: ユーザーが公開を明示するまで、robots.txt の `Disallow: /` と到達制限をかけてデプロイする。到達制限はデプロイ前にユーザーに選んでもらう——Basic認証（ID固定 `kuroco`、PWは `kuroco`／ランダム8文字（推奨）／ユーザー指定）または IP制限（**KurocoFrontとAPIの両方**に同じ範囲。管理画面・Admin MCPは認証があるため不要、Kuroco Filesのファイル配信IP制限は構築時はかけない）。完了時に URL・ID・PW を3点セットで提示し、公開指示が出たら robots.txt と制限を**セットで**外して再デプロイする（詳細は `/kuroco-frontend-integration` の「非公開デフォルト」）
   - **Admin MCP直接デプロイ**: ビルド出力をzip化 → `files-create_temp_upload_url` でアップロード → `kuroco_front-deploy`。GitHubリポジトリ不要でエージェントが完結できる。まず `is_preview: true` でプレビューデプロイし、`stage_url` をユーザーに確認してもらってから本番デプロイする。デプロイは非同期（キュー投入）なので `kuroco_front-history` で反映を確認する
   - **GitHub連携**: 管理画面 [KurocoFront] → GitHubリポジトリ連携（push時にGitHub Actionsでビルド・デプロイ）。継続的な運用に入る場合はこちらを案内する
   - ローカル確認のみならその旨と起動手順を提示する

## フェーズ5: 最終セキュリティ点検（必須）

**構築の締めは必ず `/kuroco-security-audit` を通す。** フェーズ2〜4で設定した認証方式・CORS・権限・
到達経路制限が設計どおり入っているかは、記憶ではなく設定値の読み取りで確かめる。
**実施は本番デプロイの前**（4-3のプレビューデプロイ後）。公開済みの案件に途中から入った場合は公開状態のまま点検する。

### 5-1. 監査の実行

監査スキルは**読み取り専用**。Step 1 で聞かれる前提は**こちらから渡す**（渡さないと推測できず「要検討」ばかりになる）:

| 渡す情報 | 出所 |
|---------|------|
| 対象サイト（本番／ステージング） | 0-6 の `whoami` の `site` |
| サイトの前提（完全公開／会員限定／社内） | 0-1、0-5① |
| 決定済みの認証方式と到達経路の制限 | 0-5①②。**「意図してこうした」を伝えると誤検知が減る** |
| 公開先と公開URL | 4-3（CORS判定の材料） |
| 作ったAPI定義・エンドポイントの一覧と用途 | 3-1の対応表。**試作・検証用はそれと明記** |

### 5-2. 指摘の反映

該当フェーズに戻って直す。修正は書き込みなので[ゲートの定義](#前提が満たせないときの既定動作)どおり承認を取る。

| 監査の指摘 | 戻る先 |
|-----------|-------|
| A1・A2（認証方式が設計と違う／非公開データに静的トークン） | フェーズ3-2。0-5① の判断表に戻る |
| A3・A4（CORSに開発用オリジンが残る） | フェーズ3-2。実際の公開URLだけに絞る |
| A5（会員限定データのエンドポイントが `None`） | フェーズ3-1・3-2。0-3の権限マトリクスと突き合わせる |
| **A7（未使用API／エンドポイント）** | **フェーズ3-1。試作・検証で作って使わなくなったものは無効化する**（構築中に最も溜まりやすい）。手順と注意は 0-7 と同じ。**コピー元由来のものが出てきたら 0-7 の棚卸し漏れ** |
| A6（流量制限）・A8（APIのIP制限） | フェーズ3-2。0-5② と照合 |
| B・C系（管理画面のIP制限・パスワードポリシー・2要素認証） | サイト全体の設定。**構築の範囲外なので運用者への申し送りに残す** |
| KurocoFront の Basic認証・IP制限 | フェーズ4-3。`kuroco_front.json` の `basic` / `ip_restrictions` |

**直さない指摘も落とさない。** 「サイト前提から見て許容する」「運用者の判断待ち」は理由と受容者を1行書く。

### 5-3. 修正後の再監査

**通しで再実行する。** 設定変更は他項目に波及する（セキュリティ方式の変更でトークンが無効化される、
CORSを絞って別オリジンの正常系が落ちる、権限変更が他画面に効く）ため、直した項目だけの確認では
修正が生んだ別の指摘を見落とす。**全項目そろって問題ない状態を確認してから完了報告する。**
指摘が残る場合は、残っている指摘とその扱いを添えて報告する。

### 前提が満たせないとき

| 状況 | 既定動作 | 記号 |
|------|---------|------|
| 監査スキルが読めない | 自分の知識で A1〜A8 相当だけ点検し「未検証」と明記 | `[~]` |
| Admin MCP 未接続で設定値が読めない | 点検項目と確認手順を書き出して停止。**「未点検」を「問題なし」と書かない** | `[!]` ＋「Admin MCP の接続」 |
| 修正の承認が得られない | 指摘一覧を残して停止。**未対応の指摘を残したまま「完成」と報告しない** | `[!]` ＋「修正内容への承認」 |

## パターンB・Cの補足

パターン（A/B/C）の選び方は[0-2. 進め方パターンの決定](#0-2-進め方パターンの決定)を参照。ここでは選択後の運用を補足する。

### フェーズが丸ごと担当外になる場合

順序の入れ替えではなく、**フェーズが自分の担当から外れる**ケースがある。代表例はパターンC（フロントエンドを別チームが作る）で、この場合フェーズ1（モック構築）とフェーズ4-1/4-2（実データ接続）は自分では実施しない。

- 該当フェーズの進行チェックリスト項目は **`[-]`（担当外）** を使い、`（担当外: フロントチーム）` と担当を併記する。**行は削除しない**
- 0-1 のヒアリングのうち「画面一覧」は、自分が実装しないとしても**省略しない**。エンドポイントの粒度（一覧に何件返すか、詳細に何を含めるか）はこれで決まる。相手チームに確認できない場合は仮の画面構成を置き、`04_確認事項` 相当に「画面構成が変わるとエンドポイント粒度も変わる」と影響範囲を1行で書く
- フェーズ1をやらないぶん、**モック契約の突き合わせ（フェーズ3-3）が失われる**。代わりに、作成したエンドポイントを実際に1回呼び、返ったJSONを仕様書に転記して裏取りする

### API仕様書を納品物にする場合

「API仕様書の提示がゴール」のときは、次を満たして初めて引き渡せる状態になる。

| 含めるもの | 補足 |
|-----------|------|
| エンドポイント一覧（メソッド・パス・用途） | `api-export_openapi` の OpenAPI 3.1.0 を機械可読版として併せて渡す |
| **実際に呼んで得たレスポンス例** | 推測のサンプルではなく実レスポンス。`errors` / `messages` を含む全体形で載せる |
| 認証方式と、フロント側に必要な実装 | 0-5 の決定結果。Cookie認証なら `credentials: 'include'` の要否まで |
| エラーレスポンスの形 | → `references/mock-contract.md` |
| **CORS の申し送り** | 相手チームのオリジンが未確定なら、**プレースホルダにして「確定後に管理画面で追加が必要」と明記する**。推測のオリジンを設定して済ませない |
| フィールド対応表（API項目 ↔ 画面表示） | 拡張項目の実キー名（`ext_slug` を設定していればスラッグ）を含める |
| 既知の制約 | レスポンスに出ない項目（予約公開日など）、キャッシュ、流量制限 |

### 新規API定義を作るか、既存APIに相乗りするか

- **既存APIに追加する**: 認証方式・CORS が今回の要件と一致していて、同じフロントから使う場合
- **新規API定義を作る**: 認証方式が違う場合（例: 既存が Cookie 認証で、今回は認証なしの公開APIが欲しい）。**セキュリティ方式はAPI定義単位の設定なので、方式が違うなら分けるしかない**
- 判断の前に `api-list` で既存API定義とそのセキュリティ方式を確認する。決めた理由を成果物に1行書く
- **相乗り先の候補は 0-7 で「流用する」と判定したAPI定義だけ。** コピー元由来で用途の分からないAPIに相乗りしない（認証方式・CORS・発行済みトークンを意図せず引き継ぐ）

## アンチパターン

| してはいけないこと | 理由・正しいやり方 |
|------------------|------------------|
| モックを画面専用の適当な形で作る | 差し替え時に全画面を書き直すことになる。最初からKurocoレスポンス形（契約）で作る |
| 画面確定前にコンテンツ定義を作る（**パターンBを選んだ場合を除く**） | フィールド変更のコストが高い。画面から逆算して一度で作る |
| UIコンポーネントから直接fetchする | モック/実APIの切り替えができない。必ずクライアント層を挟む |
| Admin MCPのツール名を推測して**呼び出す** | 命名は動的生成。一覧に無い名前で呼び出さない。ただし**設計書・手順書に候補として記載するのは可**（実行前に `tools/list` の実名と `inputSchema` で照合する、と併記すること） |
| 標準機能（お気に入り・コメント・フォーム・多段承認等）を自前実装する | まずマッピング表でKuroco標準機能に対応付ける。**申請・承認・差し戻しは承認ワークフローで賄えることが多い**（0-3） |
| 画面・ロール・状態の列挙が曖昧なままフェーズ1に入る | レビューで画面ごと作り直しになる。叩き台の列挙を出して差分を直してもらい、0-1で確定させる |
| 複数データの状態を1本のステータス列挙に混ぜる | 状態を動かす主体と状態を持つデータがずれる。データ種別ごとに状態機械を分ける（0-1・0-3） |
| 書き込み系ツールを確認なしで実行する | INSERT/UPDATE/DELETEは必ずユーザー確認後に実行 |
| 試作・検証用に作ったAPI／エンドポイントを有効のまま残して完了にする | 見直し対象から漏れた攻撃面が残る。フェーズ5で洗い出し、使わないものは無効化する（無効化は発行済みトークンの削除を伴うため確認を挟む） |
| セキュリティ点検を省いて「完成しました」と報告する | 設定が設計どおり入っている保証がない。フェーズ5は必須。点検できなかった場合は「未点検」と明記して止まる |
