# 機能→Kuroco機能マッピング詳細

アプリの要件をKurocoの標準機能に対応付けるためのリファレンス。
**原則: カスタム実装を検討する前に、この表でKuroco標準機能に対応付けられないか確認する。**

## ヒアリング項目

フェーズ0で確認する質問（SKILL.md 0-1 の表の具体形。**番号は 0-1 の表と1対1で対応する**）。**列挙が必要な項目は自由記述を待たず、下の「アプリ類型別のプリセット」から叩き台を出して差分を直してもらう。**

1. **アプリの目的と業務範囲**: 何のためのアプリで、どこからどこまでを扱うか（例: 購買申請から請求書照合まで）
2. **アプリの種類**: ブログ・メディア / コーポレート / 会員制サイト / 一覧+詳細型アプリ（レシピ・ポートフォリオ・イベント等）/ 社内業務システム（申請・承認・工程管理） / EC / その他
3. **利用者の役割（ロール）**: 列挙してもらう（例: 申請者・部門長・購買担当・経理担当・管理者）。ロールごとに「見える範囲」「できる操作」が違う点まで確認する
4. **画面一覧**: 番号付きで列挙（トップ / 一覧 / 詳細 / 作成・編集 / 承認待ち / マスタ管理 / ダッシュボード / ログイン / マイページ / フォーム …）
5. **扱うデータの種類と親子関係**: 何を何種類扱うか。**1件に複数明細を持つデータがあるか、明細の項目と想定行数**（例: 申請1件に明細20行、明細は品名・数量・単価・税率）
6. **データごとの状態（ステータス）**: データ種別ごとに列挙。各状態について「誰が」「何をすると」「次はどこへ」進むか、差し戻し・取り下げの有無
7. **添付ファイル**: 種類と用途（例: 見積書・仕様書・契約書）、1件あたりの想定枚数
8. **必要な機能**: ログイン / 検索・絞り込み / お気に入り / コメント / 問い合わせ / グラフ・集計 / 変更履歴・監査ログ / 通知（メール・Slack）
9. **想定規模**: 利用者数、データ件数／年、同時利用の想定
10. **デバイス方針**: PC中心か。モバイルで使う画面はどれか（全画面か、特定画面だけか）
11. **デザイン方針と使うUIパターン**: トーン（例: 落ち着いた管理画面）と、使う部品の列挙（サイドバーナビ / ステータスバッジ / テーブル / 検索・フィルター / グラフ / タイムライン）
12. **デモ／サンプルデータの要件**: 投入するマスタとトランザクションの種類。**代表1件は具体値まで**（例: 新入社員8名分のPC・モニター購入申請、金額1,248,000円、2社の見積添付）
13. **他システムとの連携予定**: 連携先とデータの向き（取得のみ／送信のみ／双方向）。連携がある場合はパターン（直接呼び出し／プロキシ／取り込み）をSKILL.md 0-4で決める
14. **フレームワーク／公開方法**: 指定がなければ**アプリの類型名ではなくSKILL.md 1-1の判定条件**（クロールの要否／非エンジニアが再デプロイできるか）で選ぶ。公開方法は KurocoFrontへデプロイ / ローカル確認まで / 既存ホスティング

## 明細（1対多）の持ち方

5でヒアリングした想定行数で選ぶ。**判断は `/kuroco-content-structure`（Part 1 の 1. TopicsGroupの分割・2. JSON項目）に渡す**が、選択肢の性格は次のとおり。

| 持ち方 | 向くケース | 注意 |
|--------|-----------|------|
| 繰り返しフィールドグループ（`group_repetitions`） | 行数の上限が決まっていて、管理画面でも編集させたい | 上限はサイト設定に依存する（`whoami` の `site.limits.topics_ext_group_loop`）。行数を推測して設定しない |
| JSON項目 | 行数が可変・多い。明細単体での検索や絞り込みが不要 | 明細の項目でのfilter・並び替えができない |
| 別コンテンツ定義＋リレーション | 明細単体を検索・集計したい、明細に独自のステータスを持たせたい | 取得が2段になる（親と子で別エンドポイント、または `relation` フィールド経由） |

### 記入時の注意（テンプレートには含めない）

- **条件を書くだけで終わらせず、「実現機構」列に何で実装するかを書く。** 「自分のものだけ」はパラメータ1つ、「自部門だけ」「自分に割り当てられた分だけ」はカスタム処理が必要になることもあり、**同じ見た目の1行でも工数が桁違い**。機構を書かないと、合意の時点でその差が見えない。型ごとの機構と使うパラメータは SKILL.md 0-3「レコードスコープの3つの型」が正。
- **上の例の「申請者自身の承認を許可する」を無効にする設定は、申請者と承認者が別人でいられることを前提にしている。** 承認者が1名しかいない／承認者も申請する運用では**有効にする**——無効のままだと承認者自身が出した申請を誰も承認できず恒久的に詰まる。前提が反転することを権限マトリクスの該当行に書く。
- **「同じグループのメンバーの投稿だけ見せる」は標準機能にない。** グループ制限・`my_own_list`／`self_only`・MemberCustomSearchAuth のどれで表現できるかを `/kuroco-auth-design` で確認し、**できないものはカスタム処理が必要な行として明示する**（要件を落とさず、工数を見えるようにする）。
- 画面一覧の「実装主体」列は、**書き手が少人数で管理画面を使える場合に投稿・編集画面をフロントに作らない選択**を可視化するためのもの（SKILL.md 0-3 成果物1参照）。

## アプリ類型別のプリセット

よくある依頼はこの構成から出発し、ヒアリングで差分を詰める:

### ブログ・メディア
- コンテンツ定義: 記事（画像 / 本文 / カテゴリ / タグ / 関連記事）
- エンドポイント: `list`（カテゴリ・タグfilter、キーワード検索付き）, `details`
- 画面: トップ（新着）、一覧（絞り込み）、詳細、検索

### コーポレートサイト
- コンテンツ定義: お知らせ、実績、（固定ページはフロント側 or ページ用定義）
- エンドポイント: `list` / `details` ×定義数、`InquiryMessage::send`（問い合わせ）
- 画面: トップ、お知らせ一覧・詳細、会社概要（静的）、問い合わせフォーム

### 社内業務システム（申請・承認・工程管理型）
- ロール: 申請者 / 承認者（部門長等） / 実務担当（購買・経理等） / 管理者。**ロールごとに「見える範囲」が違うので、ロール列挙と同時にレコード単位の制限も聞く**
- コンテンツ定義: 申請（+明細）、マスタ（部署・取引先・予算）、（必要なら）ログ
- 状態: 承認までは承認ワークフロー、承認後の工程は `select` の状態項目（`searchable: true`）で持つ
- エンドポイント: `list` / `details` / `insert` / `update`、`waiting_for_approval_list` / `accept` / `reject`、`login` / `profile`、マスタの `list`
- 画面: ダッシュボード、申請一覧（絞り込み）、申請作成、申請詳細（承認タイムライン）、承認待ち一覧、工程別の管理画面、マスタ管理、（必要なら）監査ログ
- 認証: ログイン必須。会員グループ設計とレコード単位の制限は `/kuroco-auth-design`

### 会員制・アクション付きアプリ（レシピ・イベント等）
- コンテンツ定義: メインコンテンツ（+マスタ用テーブルデータ）
- メンバー: 会員グループ、認証（フロントとAPIを同一親ドメインに揃えられるならCookie、クロスドメインSPAは動的アクセストークン。判断基準は `/kuroco-frontend-integration` のサードパーティCookie問題を参照）
