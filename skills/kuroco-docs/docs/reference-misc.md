# EC決済方法別設定

> 元ページ: `reference/ec-paymet-setting` ｜ 公式ページ: https://kuroco.app/ja/docs/reference/ec-paymet-setting/
> 概要: EC機能の支払方法設定から決済方法ごとの支払い方法を設定する際の、各項目について説明します。

## 概要
EC機能の[支払方法設定](/ja/docs/management/ec-paymenttype-list/)から決済別の支払い方法を設定する際の各項目の説明です。

### クレジットカード決済
1. 「支払い回数」を設定してください
- 1回払いのみ
- 1回払い・分割払い・ボーナス1回払い
- 1回払い・分割払い

### 月次クレジットカード（クレジットカード継続課金）決済
1. 「支払い月」を設定してください。
- 繰り返し指定: 毎月払いの場合は「01ヶ月ごと」、年間1回払いの場合は「12ヶ月ごと」を設定
- 決済月指定: 指定月に決済する場合は該当の月をカンマ区切りで指定  
  例）1,4,7,10の場合は四半期毎に決済する。
2. 「支払開始日」を設定してください、指定した月を過ぎた最初の月初から決済が開始されます。
  未設定の場合は購入翌月からの決済となります。
3. 「支払いオプション」を設定してください。
- 月単位支払い＋購入時支払い: 購入時に初回の与信・売上処理が行われ、その後は毎月月初に与信・売上処理が行われます。
- 月単位支払い（キャンセル時当月支払なし）: 購入翌月以降、毎月月初に与信・売上処理が行われます。
  ※初月無料扱いとなります、無料期間中にキャンセルした場合でも課金は行われません。
- 月単位支払い（再購入時当月支払あり）: 購入翌月以降、毎月月初に与信・売上処理が行われます。
  ただし、キャンセル後の再購入時には購入時に与信・売上処理が行われます。

**★年間1回払いなどもあるので「月次クレジットカード」の名称を「クレジットカード継続課金」に統一したい**

### コンビニ決済
1. 「支払い期限日」を設定
- 購入後、コンビニで支払いを済ませるまでの期限日を設定します。

### SPキャリア継続課金決済
1. 「月単位決済日」を設定してください。
- 毎月この日付にSPキャリア側の決済処理が行われます。
2. 「支払いオプション」を設定してください。
- 月単位支払い＋購入時支払い: 購入時に初回のキャリア側決済処理が行われ、その後は毎月月単位決済日に都度キャリア側の決済処理が行われます。
- 月単位支払い（キャンセル時当月支払なし）: 購入時にはキャリア側決済処理は行わず、その後毎月の月単位決済日のタイミングで都度キャリア側の決済処理が行われます。
- 月単位支払い（再購入時当月支払あり）: 「月単位支払い（キャンセル時当月支払なし）」と同じ挙動となりますが、過去に同一商品をキャンセルした注文が存在した場合には「月単位支払い＋購入時支払い」と同じく、購入時に初回のキャリア決済します。
※こちらはキャンセル→注文を連続で繰り返した場合、3回目以降も都度決済が行われますので注意してください。

# ECポイントの仕様とポイント更新・履歴取得API

> 元ページ: `reference/ec-point` ｜ 公式ページ: https://kuroco.app/ja/docs/reference/ec-point/
> 概要: ECポイントの残高・ポイント履歴・ロット管理の仕様と、ポイント更新API（ECPoint::update）・ポイント履歴取得API（ECPoint::history）の利用方法を説明します。

Kurocoのメンバーが保有するECポイントの管理仕様と、外部システムからポイントを操作・参照するためのAPIについて説明します。

- **ポイント更新API（`ECPoint::update`）**: メンバーのポイントを付与・消費します。
- **ポイント履歴取得API（`ECPoint::history`）**: メンバーのポイント履歴と現在残高を取得します。

## ポイントの基本概念

- メンバーごとに**ポイント残高**（合計ポイント）を持ちます。
- 残高の増減はすべて**ポイント履歴**に記録され、ポイント履歴が正式な記録です。メンバーの「更新履歴」にはポイントの変更は記録されません。
- ポイントの付与は**ロット（付与1件）単位**で管理され、各ロットは「**残ポイント**」（そのロットの未消費分）を持ちます。
- 消費は**失効期限の近いロットから順**に充当されます。失効期限のないロットは最後に充当されます。

### ポイントステータスと性質

| | 確定ポイント | 仮ポイント | 失効ポイント |
|---|:---:|:---:|:---:|
|残高に含まれる|✅|❌|❌|
|消費に利用できる|✅|❌|❌|
|仮ポイント確定バッチの対象|❌|✅（確定日到来で確定になり残高に加算）|❌|
|ポイント失効バッチの対象|✅（失効日超過で**未消費分のみ**失効）|❌|❌|

### 仮ポイントが発生する操作と確定のタイミング

仮ポイントは以下の操作で発生します。確定のタイミングは付与の経路によって異なります。

|付与の経路|付与時のステータス|確定のタイミング|
|---|:---:|---|
|商品購入によるポイント付与（代引き以外の支払い方法）|仮|売上処理のタイミングで確定し、残高に加算されます。ポイント設定の仮期間は適用されません。|
|商品購入によるポイント付与（代引き）|仮|売上処理のタイミングで確定日（売上処理日＋ポイント設定の仮期間）が設定され、確定日到来後に仮ポイント確定バッチで確定します。仮期間が設定されていない場合は売上処理日が確定日になります。|
|ログイン・会員登録によるポイント付与（ポイント設定に仮期間が設定されている場合）|仮|付与日＋仮期間で設定される確定日の到来後に、仮ポイント確定バッチで確定します。|
|ポイント更新API（`ECPoint::update`）で未来日の`fix_date`を指定して付与|仮|指定した確定日の到来後に、仮ポイント確定バッチで確定します。|
|メンバー編集画面のポイント詳細で「仮」ステータスの行を追加|仮|入力した確定日の到来後に、仮ポイント確定バッチで確定します。|

以下の経路では仮ポイントは発生しません。

- **ログイン・会員登録によるポイント付与（仮期間なし）**: 即時に確定ポイントとして付与されます。
- **ポイント更新API（`fix_date`未指定・当日・過去日）**: 即時に確定ポイントとして付与されます。
- **CSVアップロード / bulk_upsert API**: 残高（確定ポイント）を上書きします。
- **member/insert・member/update API（`allow_ec_point`有効時）**: 残高（確定ポイント）を直接更新します。

:::note
商品購入・ログイン・会員登録による自動付与は、[ポイント編集](/ja/docs/management/ec-point-edit/)でポイント付与条件を設定している場合にのみ動作します。商品購入では、さらに[商品設定](/ja/docs/management/ec-product-edit/)の「ポイント率」で対象の商品にポイント設定を紐付けている必要があります。ポイント更新API・CSVアップロード・メンバー編集画面での操作は、ポイント付与条件の設定がなくても利用できます。
:::

仮期間は[ポイント編集](/ja/docs/management/ec-point-edit/)画面のポイント付与条件ごとに設定します。

### ポイントの確定・失効バッチ

- **仮ポイント確定バッチ**: 確定日が到来した仮ポイントを確定にし、残高に加算します。
- **ポイント失効バッチ（日次）**: 失効日（`expire_date`）を過ぎた確定ロットの**未消費分だけ**を失効させます。すでに使った分が二重に差し引かれることはありません。失効時はポイント履歴に「ポイント失効(...)」という消費履歴が追加されます。

残高がロットの未消費分より少ない場合（履歴の直接編集などで残高とロットが一致しなくなった場合）は、**残高の範囲内でのみ減算**されます。残高がマイナスになることはなく、この場合もロットは失効になります。

バッチの実行タイミングは[デフォルトのバッチ処理 一覧](/ja/docs/reference/batch-list/)（`ec_fix_point` / `ec_expire_point`）を参照してください。

:::note
EC注文が1件もないサイトでも、ポイント履歴があれば確定・失効バッチは動作します。API/CSVで運用するポイントも失効・確定されます。
:::

## ポイント操作の経路一覧

どの経路でポイントを操作しても、**残高の変更には必ずポイント履歴が残ります**。

|操作経路|残高への反映|ポイント履歴|メンバー更新履歴|残高不足の減算|冪等キー|
|---|---|---|---|---|:---:|
|**ポイント更新API**（`ECPoint::update`）|即時（確定）。未来日の`fix_date`指定時は仮ポイント（確定日到来後に加算）|✅ 記録（理由=リクエストの`reason`）|❌ 記録されない|422エラー（何も変化しない）|✅|
|**CSVアップロード / bulk_upsert API**|上書き|✅ 差分を記録（理由=「CSVで更新」）|❌ 記録されない|—（上書きのため常に成功）|❌|
|**メンバー編集画面のポイント詳細**（行追加・確定）|即時|✅ 記録（理由=入力した内容）|❌ 記録されない|エラー表示（反映されない）|❌|
|**メンバー編集画面の合計ポイント欄**|**編集不可（表示のみ）**|—|—|—|—|
|**member/insert・member/update API**（`allow_ec_point`有効時）|上書き（確定ポイントの直接更新）|✅ 差分を記録（理由=「APIで更新」）|❌ 記録されない|—（上書きのため常に成功）|❌|
|EC注文・キャンペーン等の既存機能|従来どおり|✅ 記録|❌ 記録されない|従来どおり|❌|

:::caution
member/insert・member/update API での `ec_point` の設定・更新は、エンドポイント設定で `allow_ec_point` を有効にした場合のみ可能です（デフォルトは無効で、リクエストボディに `ec_point` を含めるとエラーになります）。`self_only` が有効なエンドポイントでは `allow_ec_point` は許可されません。この経路は残高の上書きであり、上書きによる差分はポイント履歴に記録されます（理由=「APIで更新」。増加は付与、減少は消費として記録）。冪等キーや任意の更新理由は利用できないため、外部からのポイント操作にはポイント更新APIの利用を推奨します。
:::

## ポイント更新API（ECPoint::update）

メンバーのポイントを外部システムから増減するAPIです。

### エンドポイント設定

管理画面のAPI設定でエンドポイントを作成して利用します。

|項目|内容|
| :--- | :--- |
|モデル|ECPoint|
|オペレーション|update|
|HTTPメソッド|POST|

:::caution
ポイントを発行できるAPIのため、**必ず認証必須で運用してください**。認証なしでの公開は不正なポイント発行につながります。
:::

### リクエストパラメータ

リクエストボディは `application/json` 形式です。

|パラメータ|必須|説明|
|---|:---:|---|
|`member_id`|✅|対象メンバーID|
|`point`|✅|増減ポイント（**整数のみ**。小数や数値以外はエラー）。正の値=付与、負の値=消費。0は指定不可。絶対値の上限は2,000,000,000|
|`reason`|✅|更新理由。ポイント履歴に記録され、ポイント履歴取得APIや管理画面に表示されます|
|`expire_date`|-|付与分の失効日（例: `2030-12-31`）|
|`fix_date`|-|付与分の確定日（例: `2030-12-31`）。付与（正の`point`）時のみ指定できます。**未来日を指定すると仮ポイントとして付与**され、確定日到来後に仮ポイント確定バッチで確定・残高加算されます。当日・過去日・省略時は即時確定です|
|`idempotency_key`|-|冪等キー（最大255文字）。[冪等キー](#冪等キーidempotency_key)を参照してください|

### 付与と消費の挙動

| |付与（point &gt; 0）|消費（point &lt; 0）|
|---|---|---|
|残高への反映|即時加算（確定ポイント）。**未来日の`fix_date`を指定した場合は仮ポイント**として付与され、確定日到来後に残高へ加算されます|即時減算|
|履歴の記録先|付与ポイント（`add_point`）＋残ポイント|使用ポイント（`use_point`）|
|`expire_date`|✅ 有効（省略時は無期限。過去日を指定した場合は次回失効バッチで失効します）|❌ 無視されます|
|`fix_date`|✅ 有効（未来日で仮ポイントとして付与。当日・過去日・省略時は即時確定）|❌ 422エラーになります|
|残高不足|—|422エラー。**残高・履歴とも一切変化しません**|
|充当順|—|失効期限の近い付与分から消費されます|

### レスポンス

|フィールド|説明|
|---|---|
|`point`|更新後の残高（未確定の仮ポイントは含まれません）|
|`ec_point_history_id`|作成されたポイント履歴のID|

### エラー

|コード|条件|
|---|---|
|400|JSONスキーマ違反（未知のパラメータ、型不正など）|
|401|認証エラー|
|404|メンバーが存在しない|
|422|`point`が0・整数でない・上限超過 / `reason`が空 / `expire_date`が不正な日付 / `fix_date`が不正な日付、または消費（負の`point`）との併用 / `idempotency_key`が255文字超 / 残高不足 / 冪等キーの誤った再利用|

### 冪等キー（idempotency_key）

通信タイムアウト等でリトライした際の**二重付与・二重減算を防ぐ**仕組みです。外部連携では指定を推奨します。キーには注文番号+操作種別など一意な文字列を指定します。

|再送パターン|結果|
|---|---|
|同一キー × 同一内容（`member_id` / `point` / `expire_date` / `fix_date` が同じ）|**再適用されない**。初回と同じ `ec_point_history_id` と現在残高を返します（200）。タイムアウト時は同じキーでそのまま再送すれば安全です|
|同一キー × 異なる内容（`member_id` / `point` / `expire_date` / `fix_date` のいずれかが違う）|422エラー（キーの使い回しとして拒否され、何も変化しません）|
|キー未指定・空文字|冪等チェックなし（**毎回適用されます**）|
|同一キーの同時並行リクエスト|一方のみ適用され、もう一方は初回結果を返します|

:::note
`fix_date` を省略したリクエストは即時確定を意味するため、処理済みの履歴がまだ仮ポイントの場合は「異なる内容」として422になります。また、未来日の `fix_date` で付与した仮ポイントが確定した後に、同一キー＋元の `fix_date` で再送した場合も422になります。いずれの場合も再適用はされません。
:::

## ポイント履歴取得API（ECPoint::history）

メンバーのポイント履歴と現在残高を取得するAPIです。

### エンドポイント設定

|項目|内容|
| :--- | :--- |
|モデル|ECPoint|
|オペレーション|history|
|HTTPメソッド|GET|

### 利用パターンとパラメータ

|利用パターン|指定するパラメータ|備考|
|---|---|---|
|管理・サーバー間連携（任意のメンバー）|`member_id`|メンバー不存在は404|
|メンバー向けマイページ（本人のみ）|`self_only=1`|`member_id` は無視されます。未ログインは401|
|ページング|`cnt`（1ページ件数）/ `pageID`（ページ番号）|`cnt` は省略時20件|
|件数のみ|`only_count=1`|`list` は空になり、`pageInfo` は `totalCnt` のみ、`total_point` は返却されません|

### レスポンス

|フィールド|説明|
|---|---|
|`total_point`|現在の残高|
|`pageInfo`|`totalCnt` / `perPage` / `pageNo` / `totalPageCnt`|
|`list`|履歴の配列（新しい順）|

`list` の主なフィールドは以下のとおりです。

|フィールド|説明|
|---|---|
|`add_point` / `add_reason`|付与ポイントと理由|
|`use_point` / `use_reason`|消費ポイントと理由|
|`point_status`|1=確定 / 2=仮 / 3=失効|
|`remaining_point`|付与ロットの**未消費残**。消費や失効で減少します|
|`fix_date`|確定日|
|`expire_date`|失効予定日（無期限の場合はnull）|
|`inst_ymdhi` / `update_ymdhi`|作成・更新日時（ISO 8601）|

:::note
管理者名などの内部情報や他システムの冪等キーはレスポンスに含まれません。
:::

## メンバーCSVアップロード・bulk_upsert APIでのポイント上書き

メンバーCSVアップロードの `ec_point` 列でポイント残高を上書きできます（bulk_upsert APIも同じ挙動です）。

|CSVの内容|残高|ポイント履歴|
|---|---|---|
|`ec_point` 列があり、現在より大きい値|上書き|✅ 差分を**付与**として記録（理由=「CSVで更新」）|
|`ec_point` 列があり、現在より小さい値|上書き|✅ 差分を**消費**として記録|
|`ec_point` 列があり、現在と同じ値|変化なし|記録されない|
|`ec_point` 列があり空欄 ＋ 空更新設定ON|クリア（空）|✅ 従来残高の全額を消費として記録|
|新規メンバーの行に `ec_point` あり|初期値として設定|✅ 初期残高を付与として記録|
|**`ec_point` 列がない**|**一切変化しない**（従来どおり）|記録されない|

:::note
残高の上書き後にポイント履歴の記録に失敗した行がある場合は、「会員データは更新されましたが、ポイント履歴の記録に失敗しました。」というエラーが表示されます。この場合、該当行のメンバーデータ（残高の上書きを含む）自体は更新されています。
:::

アップロード手順は[メンバーアップロード](/ja/docs/management/member-upload/)を参照してください。

## 管理画面（メンバー編集）でのポイント操作

:::note
ECを利用していないサイトでメンバー編集画面のポイント情報タブを利用する場合は、サイト管理画面の[ECポイント機能](/ja/docs/management/site-settings/#メンバー)を有効にします。ECを利用している場合、ポイント機能は本設定に関わらず利用できます。
:::

- **合計ポイントの直接編集欄は廃止**され、表示のみになります。
- ポイント詳細（履歴）テーブルに**「残ポイント」列**が追加され、確定付与ロットの未消費残（消費・失効の進み具合）が確認できます。

ポイント詳細への行追加のステータス別挙動は以下のとおりです。

|追加する行のステータス|残高への反映|備考|
|---|---|---|
|確定 × 付与|即時加算|残ポイント付きのロットとして記録されます|
|確定 × 消費|即時減算|**残高不足の場合は保存前にエラー**になり、メンバー情報を含めて保存されません|
|仮|反映されない|確定バッチで確定日到来時に加算されます|
|失効|反映されない|記録のみ|

:::info
- 確定ステータスの行では、付与と消費を同じ行に同時に入力できません。
- **確定ステータスの既存の履歴行は編集・削除できません**。また、既存行のステータスを確定へ変更することもできません。仮ポイントの確定は仮ポイント確定バッチで行われます。
:::

画面の項目説明は[メンバー](/ja/docs/management/member/)を参照してください。

## 注意事項・制限

- **member/insert・member/update API での `ec_point` の設定・更新は、エンドポイント設定で `allow_ec_point` を有効にした場合のみ可能です**（デフォルトは無効で、リクエストに含めるとエラーになります。`self_only` が有効な場合は許可されません）。この経路は残高の上書きであり、上書きによる差分はポイント履歴に「APIで更新」として記録されます。冪等キーや任意の更新理由は利用できないため、ポイントの外部操作は、ポイント更新API / bulk_upsert API / CSVアップロードのいずれかの利用を推奨します。
- ポイント失効バッチで失効するのは「未消費分のみ」です。使用済み分を含む全額が失効する挙動ではありません。

# Kurocoにおける制限事項

> 元ページ: `reference/limitations-in-kuroco` ｜ 公式ページ: https://kuroco.app/ja/docs/reference/limitations-in-kuroco/
> 概要: Kurocoのご利用における制限事項を説明します。

## Kurocoにおける制限事項
Kurocoのご利用における制限事項を説明します。

### コンテンツ
#### ID
- topics_idをはじめとするIDは自動採番となり、アカウント作成元のデータを引き継ぐ仕様上、1から始まらない事があります。

#### コンテンツ数
- topics_idは `1`～`2,147,483,647` の値をとります。  理論上は21億件のコンテンツを登録できることになりますが、21億件ある場合の動作検証はしておりません。  
  データの項目などによりますが、100万件以内がパフォーマンスする想定です。それ以上をご利用の場合はご相談ください。

#### 並び順
- 並び順に入力できる値は9桁までとなります。

#### Slug
- Slugは2048文字までしか登録できません。
- 使用可能な文字は半角英数字とハイフン（-）のみです。日本語は使用できません。

#### テキスト文字数制限
- 無制限・ただし、20万文字以内/フィールド毎を推奨

#### インデックス付与
- コンテンツの項目で「インデックス付与」されている場合は2048文字までしか登録できません。

#### CSVインポート
- 100MB以内のCSVファイル・ただし、3万件以内を推奨（拡張予定あり）

#### コンテンツ定義数
- 無制限・ただし、1,000個以内を推奨

#### コンテンツカテゴリ数
- 無制限・ただし、コンテンツ定義毎に1,000個以内を推奨

### API
#### 同時接続数
- APIに対して最大同時接続数の制限が設定されており、制限を超えると429エラーが返ります。
  - キャッシュしていないAPIアクセス：ホスト名毎に同時接続数:200  
    仮にAPIレスポンスに300msかかるエンドポイントを想定すると、0.3秒の間に200以上のリクエストを受けることになり、ほとんどのお客様は制限にかかることはありません
  - キャッシュしているAPIアクセス：同時接続数:制限なし

#### 管理API・Admin MCPの書き込みリクエスト
- 管理API（`/direct/rcms_api/admin_api/`）とAdmin MCP（`/direct/rcms_api/admin_mcp/`）への書き込みリクエストは、サイト毎に2秒あたり8リクエストまでです。制限を超えると429エラーが返ります（`Retry-After`ヘッダで再試行可能になるまでの秒数を返します）。
  - 読み取りリクエストはこの制限の対象外です（上記の同時接続数の制限は別途適用されます）。
  - MCPクライアントは1つの指示を複数のツール呼び出しに展開して並列で送信することがあるため、書き込みは1件ずつ送信するか、1回の呼び出しで複数件を処理する一括操作をご利用ください。
- 1回の呼び出しで処理できる件数は200件まで、`async=true`でジョブとして登録する場合は1ジョブで100,000件までです。
  :::info
  - [MCPサーバリファレンス](/ja/docs/reference/mcp-server/#制限事項)
  :::

#### エンドポイント数
- 無制限・ただし、1,000個以内を推奨

#### APIキー数
- 無制限・ただし、1,000個以内を推奨

#### QuerySting
- QueryStingの最大長は8000文字程度となっています。

### メンバー
#### メンバー数
- 1000万人投入実績あり・ただし、30万人以上は事前相談推奨

#### CSVインポート
- 100MB以内のCSVファイル・ただし、3万件以内を推奨（拡張予定あり）

#### パスワード
- 使用可能な文字：半角英数字（大文字小文字は区別される）と一部の記号（`-`、`_`、`&`）
- 全角文字は使用できません。
- 最小・最大文字数は[環境設定] -> [サイト管理]で変更可能です。
  :::info
  - [メンバー管理のパスワードに利用できる文字を教えてください](/ja/docs/faq/what-characters-are-allowed-in-passwords/)
  :::

### ファイル
#### Kuroco Files
- Kuroco Filesにアップロードできるファイルの最大容量は80MB程度となっています。  
  80MBを超えるファイルをアップロードしたい場合はGCS,S3との連携をご検討ください。
  :::info
  - [コンテンツ投稿時にアップロードできるファイルの最大容量を教えてください。](/ja/docs/faq/what-is-the-maximum-size-of-files-that-can-be-uploaded/)
  :::

- ファイルマネージャーで利用できるファイルの種類は以下で確認してください。
  :::info
  - [ファイルマネージャーで利用できるファイルの種類](/ja/docs/reference/what-file-formats-does-the-file-manager-support/)
  :::

#### Kuroco Front
- Kuroco Frontにアップロードできる最大ファイルサイズは30MBとなっています。
- サーバーサイドプログラム（PHP、CGI、Perl、Ruby等）は動作しません。
- SSI（Server Side Include）、.htaccessは利用できません。
  :::info
  - [KurocoFrontの利用に制限事項はありますか](/ja/docs/faq/are-there-any-restrictions-on-using-kurocofront/)
  :::

### URL/ドメイン
#### ドメイン
- 日本語ドメインはブラウザの挙動に依存するため、ご利用を推奨しておりません。
  - OK: `https://example.com`
  - 非推奨: `https://てすと.com`

#### ltdフォルダのトークン
- ltdフォルダのファイルにつく`t=...`のトークンの有効期限は15分です。
- 有効期間の変更は行えません。
  :::info
  - [ltdフォルダのファイルにつくt=・・・のURLの有効期限はいくつですか？](/ja/docs/faq/how-long-is-the-t-url-in-the-ltd-folder-valid/)
  :::

#### GCS/S3ファイルの有効期限
- GCS/S3に保存したファイルのURLには有効期限があります。
  | パターン | 有効期限 |
  |---------|---------|
  | APIキャッシュ期間が7日以内 | APIキャッシュ期間＋30秒 |
  | APIキャッシュ期間が7日以上 | 7日 |
  | APIキャッシュなし | 30分またはセッション時間＋30秒の短い方 |
  | パブリックフォルダ | 無期限 |

  :::caution
  SSGなどでこちらのURLを長期間使用していると有効期限切れになる恐れがあります。
  :::
  :::info
  - [GCS, S3に設定したファイルの有効期限について](/ja/docs/reference/expiration-for-files-in-gcs-and-s3/)
  :::

### 無料利用ユーザーの制限
無料利用ユーザー（決済情報未登録のユーザー）には、以下の制限が適用されます。

:::info
以下の条件に該当する場合は制限対象外となります:
- 「[請求情報](/ja/docs/management/site-payment/)」でクレジットカードをご登録いただいているお客様
- 決済手段に「ディバータから請求書」と表示されているお客様
:::

#### メール送信
- **1時間あたり約100通**までの送信制限があります。
- ご自身のSendGridのAPIキーを利用して、独自ドメインのメールアドレスをご利用されている場合は制限対象外となります。

:::info
お知らせ -> [無料利用ユーザーのメール送信数に制限をかけます](/ja/docs/information/2025-11-26/)
:::

#### バッチ処理
- **1時間あたり約100件**までの実行制限があります。カウントされるのはバッチの起動（登録）回数で、バッチ内で発行されるリクエスト数ではありません。
- 1回のバッチ実行は既定で4時間、Smartyテンプレートを実行するバッチは6時間でタイムアウトします。大量データはページング等で分割し、1回の実行を短く保ってください。

:::info
お知らせ -> [無料利用ユーザーのバッチ処理・API送信に制限をかけます](/ja/docs/information/2026-01-27/)
:::

#### API送信
- **1時間あたり約1,000件**までの送信制限があります。

:::info
お知らせ -> [無料利用ユーザーのバッチ処理・API送信に制限をかけます](/ja/docs/information/2026-01-27/)
:::

# 管理画面プラグインで利用可能なスロット一覧

## スロットについて

管理画面プラグインの設定時には以下の項目を設定し、プラグインの配置箇所や表示条件を明示する必要があります。それぞれの設定項目の役割について説明します。

- スロット
- スロットパラメータ

### スロット
スロットとは、管理画面上で挿入または差し替え可能なプラグインの位置を示す識別子です。適用対象ページのURLとスロットを共に設定することで、指定した箇所にプラグインを配置します。

### スロットパラメータ

スロットパラメータとは、各スロットのプラグイン表示条件を指定するためのパラメータです。例えば、特定のIDに一致するページにのみプラグインを設定する場合などに利用します。利用可能なパラメータはスロット毎に異なります。

# 同期項目一覧

> 元ページ: `reference/sync-site-data` ｜ 公式ページ: https://kuroco.app/ja/docs/reference/sync-site-data/
> 概要: Kurocoでは、親サイトと子サイト間でサイトデータを同期できます。この同期機能により、本番環境で使用しているコンテンツや設定を、開発環境へ反映させることが可能です。

Kurocoでは、親サイトと子サイト間でサイトデータを同期できます。  
この同期機能により、本番環境で使用しているコンテンツや設定を、開発環境へ反映させることが可能です。

本リファレンスでは、サイトの同期方法と同期の種類について説明します。

:::tip
- 同期機能は親サイトのみ利用可能です。子サイトの管理画面には表示されません。
- 親から子、子から子など、同期の方向については制限がありません。
:::

## 同期方法
[環境設定] -> [サイト一覧]をクリックし、サイト一覧画面を表示します。

![Image (fetched from Gyazo)](https://t.gyazo.com/teams/diverta/38d511e0cfe80f62971de2f3e795dbfb.png)
「同期」より下記選択し、「更新する」をクリックします。

|同期する|チェックを入れます。|
|同期元サイトキー|同期したいサイトのサイトキーを選択します。|

# WAF 検出タイプ

> 元ページ: `reference/waf-detection-type` ｜ 公式ページ: https://kuroco.app/ja/docs/reference/waf-detection-type/
> 概要: Kuroco EdgeのWAFが出力する検出タイプの一覧です。各シグナルの Name、Tags、Description を掲載しています。

## 概要
以下の情報は、さまざまなWAFタグに関する詳細を提供します:

- `Name`: 声で参照または説明するために使用できるシグナルの名前。
- `Tags`: 一致したリクエストに適用され、Kuroco Edgeログ内で検索に使用できるシグナルのタグ。
- `Description`: シグナルの意味または指示する内容の概要。

## 検出タイプのリスト

#### 攻撃

| 名前 | タグ | 説明 |
| --- | --- | --- |
| Attack Tooling | USERAGENT | 攻撃ツールは、自動化されたソフトウェアを使用して、セキュリティの脆弱性を特定したり、発見された脆弱性を試みて攻撃することです。 |
| AWS SSRF | AWS-SSRF | サーバーサイドリクエストフォージェリ（SSRF）は、Webアプリケーションによって作成されたリクエストを内部システムのターゲットに送信しようとするものです。 AWS SSRF攻撃は、SSRFを使用してAmazon Web Services（AWS）キーを取得し、S3バケットとそのデータにアクセスします。 |
| Backdoor | BACKDOOR | Backdoorシグナルは、システム上に一般的なバックドアファイルが存在するかどうかを判断しようとするリクエストです。 |
| Command Execution | CMDEXE | コマンド実行は、ユーザー入力によって任意のシステムコマンドを実行することによって、対象システムを制御または破損しようとするものです。 |
| Cross Site Scripting | XSS | クロスサイトスクリプティングは、悪意のあるJavaScriptコードを介してユーザーアカウントまたはWebブラウジングセッションを乗っ取ろうとするものです。 |
| Directory Traversal | TRAVERSAL | ディレクトリトラバーサルは、システム全体で特権付与フォルダをナビゲートし、機密情報を取得することを試みるものです。 |
| Log4J JNDI | LOG4J-JNDI | Log4J JNDI攻撃は、Log4J 2.16.0より前のバージョンに存在する_Log4Shell_脆弱性を悪用しようとするものです。 |
| SQL Injection | SQLI | SQLインジェクションは、任意のデータベースクエリを実行することによってアプリケーションにアクセスしたり、特権情報を取得したりすることを試みるものです。 |
